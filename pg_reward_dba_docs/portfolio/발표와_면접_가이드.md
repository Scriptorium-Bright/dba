# 포트폴리오 발표·면접 가이드

## 3분 발표 흐름

### 1. 프로젝트와 문제 — 30초

“게임 이벤트 보상 지급을 PostgreSQL에서 관리하는 운영 실습 프로젝트입니다. 지급 사실, 현재 지갑 잔액, 재화별 변동 원장이 서로 맞는지 확인할 수 있도록 데이터 모델을 설계하고, 지급 경쟁과 장애 상황을 직접 재현했습니다.”

### 2. 설계와 지급 정확성 — 45초

“`reward_grants`는 지급 사실, `wallets`는 현재 잔액, `wallet_ledger`는 잔액 변동 근거를 저장합니다. CLAIM은 프로시저와 DB 제약을 사용해 동시 요청에서도 지급이 한 번만 남도록 했고, 100개 요청에서 `PAID=1`, `REPLAYED=99`를 확인했습니다. BATCH는 1,000명 처리 중 중단한 뒤 실제 지급 행을 기준으로 미지급자를 계산해 재개했고 최종 대사 불일치가 없었습니다.”

### 3. 변경 배포와 조회 튜닝 — 50초

“장애 보상 기능을 추가할 때 migration을 확장과 과거 데이터 검증으로 나눴습니다. 제약 검증 실패를 데이터 문제로 확인하고 forward fix 후 재시도했으며, 새 스키마에서 구버전 API의 CLAIM도 확인했습니다. 조회 튜닝에서는 100만 건 원장의 출처 비율을 측정해 보상 행에 한정된 부분 인덱스를 적용하고, 실행계획·저장 공간·WAL·생성 중 DML을 같이 비교했습니다.”

### 4. 운영 진단과 마무리 — 40초

“Lock Wait 실습에서는 UPDATE의 waiter PID만 보는 데서 멈추지 않고 `pg_blocking_pids()`로 blocker를 찾았습니다. blocker가 `idle in transaction`인 상태와 SQL을 확인해 원인을 좁힌 뒤, 조치 후 요청 완료와 데이터 복구, 남은 Lock 여부를 다시 확인했습니다. 각 단계는 계획, 실행 기록, 재현 SQL과 도구로 정리해 같은 흐름을 따라가며 검토할 수 있습니다.”

## 기술 질문 준비

### 지급 사실, 잔액, 원장을 분리한 이유는 무엇인가요?

지갑 잔액만 저장하면 어떤 지급이 잔액을 만들었는지 추적하기 어렵습니다. `reward_grants`에 업무상 지급 사실과 snapshot을 남기고, wallet은 현재 잔액, ledger는 재화별 변동으로 나눴습니다. 세 테이블을 조회해 지급과 잔액을 서로 대사할 수 있습니다.

### 같은 CLAIM 요청이 겹치면 어떻게 중복 지급을 막았나요?

사전 조회는 동시 요청 사이의 경합을 막지 못하므로 DB의 `(event_id,user_id)` UNIQUE 제약을 최종 방어로 뒀습니다. 지급 사실 insert, wallet update, 재화별 ledger insert를 하나의 호출 트랜잭션에서 처리했습니다. 같은 request ID 재호출과 이미 지급된 다른 요청 ID도 별도 결과로 구분했습니다.

### BATCH 중단 시 완료 건수는 어떻게 판단했나요?

worker 로그 카운터만으로 완료를 판단하지 않았습니다. 대상 명단에서 `reward_grants`가 없는 사용자를 다시 계산해 미지급 대상만 처리했습니다. 종료 신호가 전달되는 동안 추가 commit이 생길 수 있어 중단 직전 카운터와 crash recovery 후 실제 행 수가 달랐고, 최종 결과는 대상·grant·미지급·대사 쿼리로 확인했습니다.

### Migration 검증이 실패했을 때 어떻게 복구했나요?

제약을 `NOT VALID`로 추가한 뒤 과거 행을 검증하는 단계에서 `LEGACY_INVALID` 데이터가 발견됐습니다. Flyway 적용 버전과 constraint의 검증 상태를 확인하고 원인 행을 유효한 source 값으로 수정한 다음 제약 검증을 다시 실행했습니다. 수정 완료 후 V9가 성공했고 catalog에서 두 제약의 `convalidated=true`를 확인했습니다.

### 부분 인덱스를 선택한 근거는 무엇인가요?

fixture에서 COMPENSATION은 100만 ledger 중 1%였습니다. 전체 source 인덱스 후보는 약 30MB였고, 선택한 부분 인덱스 2개는 각각 672KB였습니다. 전역 cursor와 기간 검색에서 각 인덱스가 선택되는 계획을 확인했습니다. 실행시간은 반복마다 차이가 있어 고정 개선률 대신 실행계획, 필터에서 제외한 행 수, buffer, 공간, WAL을 함께 설명합니다.

### 일반 인덱스 생성과 `CONCURRENTLY`를 어떻게 비교했나요?

일반 생성은 relation lock을 기다리는 동안 뒤에 시작한 UPDATE도 lock queue에서 기다렸고, 제한 시간을 둔 실행은 8초 뒤 취소됐습니다. `CONCURRENTLY`는 기존 transaction snapshot을 기다리는 동안에도 비교 DML은 완료됐습니다. 운영 조회 인덱스에 `CONCURRENTLY`를 사용하고, 생성 완료 후 catalog의 `indisready`, `indisvalid`로 상태를 확인했습니다.

### Lock Wait를 어떻게 진단했나요?

`pg_stat_activity`에서 waiter의 SQL, state, wait event를 확인하고 `pg_blocking_pids()`로 blocker PID를 연결했습니다. `pg_locks`와 blocker의 트랜잭션 상태를 함께 봐 행 잠금과 `idle in transaction`을 확인했습니다. 조치 후 대기 해소뿐 아니라 UPDATE 결과, 잔액, 남은 Lock, fixture 복구를 점검했습니다.

### 실제 장애 대응에서 먼저 확인할 내용은 무엇인가요?

지연 중인 요청과 DB 세션을 연결하고, blocker의 SQL·트랜잭션 나이·잠금 범위·영향 요청을 파악하겠습니다. 그 뒤 업무 변경이 완료 가능한지, rollback이나 취소가 필요한지 담당자와 판단하고 조치하겠습니다. 조치 뒤에는 요청 진행 여부와 데이터 정합성을 확인해 결과를 공유하겠습니다.

## 발표 자료 구성 제안

1. 문제와 서비스 데이터 흐름
2. 테이블 관계와 지급 트랜잭션
3. 동시 CLAIM 및 BATCH 복구 결과
4. 장애 보상 migration과 호환성 확인
5. 100만 원장 실행계획·인덱스 비용 비교
6. Lock Wait 진단 타임라인
7. 설계 결정, 재현 경로, 배운 점

숫자를 보여주는 페이지에는 데이터 규모, phase, 실행 SQL 또는 실행 기록 링크를 붙입니다. 실행 시간 한 건만 강조하기보다 실행계획과 함께 설명합니다.
