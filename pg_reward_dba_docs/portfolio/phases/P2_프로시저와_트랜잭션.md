# P2 | 지급 프로시저, 트랜잭션, 동시성 제어

## 한 줄 요약

CLAIM과 BATCH 지급 규칙을 PostgreSQL 프로시저로 모으고, 동시 요청·부분 실패·작업자 중단 뒤에도 실제 지급 기록을 기준으로 결과를 대사하고 재개했습니다.

## 설계와 구현

### CLAIM — 한 사용자 직접 수령

- Flyway V3의 `reward.grant_event_reward`가 이벤트 조건 확인, 지급 사실 insert, wallet update, 재화별 ledger insert를 담당합니다.
- API가 트랜잭션 경계를 소유하고 프로시저는 자체 commit을 하지 않습니다.
- 이벤트 정책 행은 `FOR SHARE`로 읽고, `(event_id,user_id)` UNIQUE와 `INSERT ... ON CONFLICT ... RETURNING`으로 동시 중복을 막습니다.
- 같은 `request_id` 재호출은 `REPLAYED`, 다른 키로 이미 지급된 사용자·이벤트 재요청은 `ALREADY_GRANTED`로 나눕니다.
- Ledger insert를 실패시킨 뒤 호출자 트랜잭션을 rollback해 grant와 wallet 변경도 함께 취소되는지 확인했습니다.

### BATCH — 대상 명단 지급

- DRAFT에서 대상 명단을 확정하고 OPEN 후에는 수정할 수 없게 했습니다.
- 이벤트별 advisory lock으로 worker 중복 실행을 막고, 사용자별 독립 트랜잭션에서 공용 지급 프로시저를 호출합니다.
- `(event_id,user_id)`에서 결정적으로 만든 request ID를 사용합니다.
- 재개할 사용자 목록은 실행 로그 카운터가 아니라 `event_recipients LEFT JOIN reward_grants`로 다시 계산합니다.
- worker 중단 뒤 남은 RUNNING 실행 기록을 정리하고 미지급자만 재처리합니다.

## 실행 결과

| 시나리오 | 결과 |
|---|---|
| 같은 사용자·이벤트·요청 ID로 100개 병렬 CLAIM | `PAID=1`, `REPLAYED=99` |
| 다른 요청 ID로 같은 사용자·이벤트 재요청 | `ALREADY_GRANTED` |
| 다른 사용자가 같은 요청 ID 사용 | HTTP 409 |
| 단일 성공 CLAIM의 DB 결과 | grant 1건, ledger 2행, 불일치 0 |
| ledger INSERT 실패 후 rollback | 남은 grant 0, 사용자 잔액 변화 없음 |
| 1,000명 BATCH worker 중단 후 재개 | 대상 1,000명, grant 1,000건, 미지급 0 |
| 최종 데이터 대사 | grant-ledger 불일치 0, wallet-ledger 불일치 0 |

Crash 실습에서 중지 신호 직전 관찰한 수는 688건이었고, 종료 신호 전달 중 추가 커밋 뒤 복구 시점에는 825건이 확인됐습니다. 재개 시 남은 175명만 처리해 최종 1,000건을 맞췄습니다.

## DBA 직무와 연결되는 판단

- 애플리케이션의 사전 조회만으로 경합을 막지 않고 UNIQUE 제약을 최종 방어선으로 뒀습니다.
- 지급, wallet, ledger를 한 호출 트랜잭션에 두어 세 데이터 중 일부만 남는 상태를 방지했습니다.
- 사용자별 commit을 사용해 한 명의 오류가 앞선 사용자의 완료분을 취소하지 않도록 했습니다.
- 작업 로그는 관측 수단으로 사용하고 완료 여부는 지급 사실과 ledger/wallet 대사로 확인했습니다.
- API 응답과 DB commit 결과를 구분해 Timeout/응답 유실 이후에도 저장된 상태를 확인할 수 있게 구성했습니다.
