# P4 | 대량 지급 이력 검색과 인덱스 튜닝

## 한 줄 요약

100만 건의 지급 원장에서 운영 조회의 실행계획을 비교하고, 보상 출처가 전체 데이터의 1%인 분포에 맞춰 부분 인덱스를 설계했습니다. 검색 계획과 함께 인덱스 저장 공간, WAL 증가, 생성 중 쓰기 대기도 측정했습니다.

## 문제와 측정 조건

운영자는 지급 이력을 최신순으로 보거나 특정 기간의 보상 내역을 조회합니다. P4 전용 DB에 EVENT 990,000건과 COMPENSATION 10,000건을 구성하고 두 검색을 같은 데이터에서 측정했습니다. 사용자 wallet과 ledger 합계 대사 결과는 0명이 불일치했습니다.

## 기준 실행계획

| 조회 | 인덱스 전 계획 | 관측 |
|---|---|---|
| 보상 최신순 100건 | 기본 키 역방향 순회 후 출처 필터 | 결과 100건 전 9,851행 제외, 2.148ms, shared hit 429/read 34 |
| 날짜 범위 | 병렬 순차 스캔과 top-N 정렬 | worker별 약 333,304행 제외, 47.817ms, shared hit 10,766 |

출처별 JOIN을 따로 수행하는 대안도 비교했습니다. 보상 행 10,000건을 읽어 정렬하는 계획이 선택되어 전역 조회 15.562ms, 날짜 조회 7.662ms였습니다. 공통 JOIN을 유지하는 계획이 해당 데이터 분포에서 더 나았습니다.

## 인덱스 설계와 결과

최종 선택은 `source_type='COMPENSATION'` 조건의 부분 인덱스 2개입니다.

1. `wallet_ledger_compensation_cursor_idx`: 최신 ID cursor 검색용 `id DESC`와 응답 필드를 포함합니다.
2. `wallet_ledger_compensation_created_idx`: 기간 검색용 `created_at DESC, id DESC`와 응답 필드를 포함합니다.

각 인덱스는 672KB였고 catalog에서 `indisready=true`, `indisvalid=true`를 확인했습니다. 비교한 전체 `(source_type,id DESC)` 인덱스 후보는 약 30MB였습니다. 최종 실행계획은 전역 조회에서 cursor 인덱스를, 기간 조회에서 created_at 인덱스를 선택했습니다.

| 최종 조회 | 관측 결과 | 실행계획 근거 |
|---|---|---|
| 최신순 100건 | 0.459ms, shared hit 404 | compensation cursor 부분 인덱스 |
| 날짜 범위 88건 | 0.242ms, shared hit 533 | compensation created_at 부분 인덱스 |

반복 측정은 전역 조회 1.136ms와 42.890ms, 기간 조회 0.253ms와 4.239ms도 기록했습니다. 실행 시간은 반복마다 달랐지만 계획은 부분 인덱스를 선택했습니다. 따라서 단일 실행 시간으로 고정 개선률을 주장하지 않고, 읽은 행과 buffer, 계획 선택을 함께 남겼습니다.

## 비용과 배포 방식

50,000행 쓰기 비교에서 PK-only의 WAL은 8,857,500 bytes, 부분 인덱스 2개를 추가한 테이블은 9,010,900 bytes였습니다. 추가량은 153,400 bytes(약 1.73%)였습니다. fixture의 보상 500건에 대해 각 부분 인덱스는 80KB였습니다. 실행 시간 차이로 쓰기 지연을 판정하지 않았습니다.

일반 `CREATE INDEX` 실험에서는 기존 트랜잭션이 relation lock을 보유할 때 DDL이 `lock_timeout=8s`로 8.07초에 취소됐고, 뒤에 시작한 UPDATE도 약 8.02초 기다렸습니다. `CREATE INDEX CONCURRENTLY`는 기존 transaction snapshot 종료를 기다렸지만, 동시에 실행한 UPDATE는 0.045초에 완료됐습니다. 인덱스 생성은 25.691초 뒤 완료됐고 `indisready=true`, `indisvalid=true`였습니다.

이 결과를 바탕으로 조회에 필요한 두 인덱스를 `CREATE INDEX CONCURRENTLY`로 배포하도록 선택했습니다. 생성 시간이 더 길어도 일반 DML이 relation lock queue 뒤에서 기다리는 현상을 줄이는 쪽이 운영 조회용 인덱스 추가에 적합했습니다.

## 설계 판단

- 전체 100만 행에 넓은 인덱스를 만들지 않고 1% 보상 ledger만 색인했습니다.
- 검색 종류에 맞는 cursor와 날짜 인덱스를 분리해 각 쿼리 계획을 확인했습니다.
- 제품 SQL의 공통 JOIN 형태는 유지하고, 검증된 출처 literal 조건으로 부분 인덱스 predicate를 판별하게 했습니다.
- `EXPLAIN ANALYZE, BUFFERS`와 실제 API 결과를 함께 확인했습니다.
- 인덱스 추가 비용은 공간·WAL·동시 DML 관측으로 남겼습니다.

## DBA 직무와 연결되는 내용

이 사례는 쿼리 최적화에서 계획만 보거나 실행시간만 보는 대신, 데이터 분포·필터 제거 행 수·buffer 접근·인덱스 크기·WAL·DDL 대기를 함께 비교한 경험을 보여줍니다. 대안 SQL이 예상과 다르게 동작했을 때 실행계획을 근거로 반영 여부를 결정했고, API로 같은 결과가 반환되는지도 확인했습니다.
