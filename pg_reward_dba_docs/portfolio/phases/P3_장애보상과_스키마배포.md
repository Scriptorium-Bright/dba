# P3 | 장애 보상과 단계별 스키마 배포

## 한 줄 요약

기존 이벤트 지급 경로를 유지하며 고객지원용 장애 보상을 추가하고, migration 확장·검증 실패·forward fix·구버전 API 호환성까지 별도 PostgreSQL 환경에서 확인했습니다.

## 변경 요구

이벤트 장애로 CLAIM이 실패한 사용자에게 추가 보상을 지급하되, 기존 이벤트 지급과 지갑 원장을 보존하고 동일 장애의 영향을 추적해야 했습니다. 이를 위해 보상 기록과 원장 출처를 확장하고, 기존 API가 새 schema 단계마다 계속 동작하는 순서를 설계했습니다.

## Schema 배포 순서와 검수

| 단계 | 변경·확인 | 결과 |
|---|---|---|
| V7 확장 | 보상 테이블과 ledger 출처 컬럼을 추가하고 기존 행에 `EVENT` 상수 기본값 적용 | 기존 CLAIM 성공. catalog에서 기본값이 기존 행을 표현하는 것을 확인해 대량 UPDATE 생략 |
| V8 제약 확장 | 출처 일관성 CHECK와 FK를 `NOT VALID`로 추가 | 신규 쓰기에 제약 적용, 과거 행 검증은 별도 단계에 둠 |
| V9 검증 실패 | `LEGACY_INVALID` source 행이 있는 상태에서 제약 검증 | V9 실패, Flyway는 V8 유지, 두 constraint는 미검증 상태 |
| Forward Fix | 원인 행을 `EVENT`로 바로잡고 V9 재시도 | V9 성공, 두 constraint `convalidated=true` |
| V10/V11 | CS 보상 프로시저와 reset 경로 호환 migration 적용 | Flyway V11, API health `UP` |
| 구버전 API 교차 실행 | 이전 API 이미지가 V11 schema에 CLAIM 실행 | HTTP 200 `PAID`, 이후 API에서 EVENT ledger 2행과 40/10 snapshot 확인 |

### DDL Lock 대기

- 세션 A가 `wallet_ledger`에서 SELECT 후 트랜잭션을 열어 `AccessShareLock`을 유지했습니다.
- 세션 B의 `ALTER TABLE`은 `AccessExclusiveLock` 대기 뒤 `lock_timeout=8s`로 8.10초에 취소됐습니다.
- 대기 중 시작한 세션 C의 SELECT도 lock queue 뒤에서 기다렸고, B timeout 이후 A 종료 전에 재개되어 6행을 반환했습니다.
- A 종료 뒤 ALTER 재시도는 0.140초에 성공했고 probe column 제거는 0.092초였습니다.

DDL 자체 실행 시간과 잠금 획득 대기 시간을 분리해 관찰했고, `pg_stat_activity`, `pg_locks`, blocker PID를 기록했습니다.

## 고객지원 보상 시나리오

P3 전용 DB에서 event 3의 `reward_grants` insert를 실패시키는 조건을 만들었습니다.

1. user 102의 CLAIM은 HTTP 500 `DATABASE_ERROR`로 끝났습니다.
2. 직후 wallet은 Money/Point `1000/200`, 해당 이벤트 grant 0건, EVENT ledger 0행, compensation 0건이었습니다.
3. 실패 조건을 제거하고 event 3을 CLOSED 처리했습니다.
4. 운영자 요청으로 Money 600 / Point 50의 보상을 지급했습니다.
5. 응답은 HTTP 200 `PAID`, compensationId 1이었고 wallet은 `1600/250`이 됐습니다.
6. 보상 snapshot과 두 재화 ledger 합은 `600/50`으로 일치했고, wallet-ledger 불일치는 0행이었습니다.

## 설계 판단

- 기존 `reward_grants`의 의미를 바꾸지 않고 `EVENT`와 `COMPENSATION`을 원장 출처로 구분했습니다.
- 확장과 과거 행 검증을 V7/V8/V9로 나눠 실패 시 적용된 schema 단계를 유지한 채 원인 데이터를 고치고 재시도했습니다.
- 상수 기본값으로 과거 행을 표현할 수 있음을 catalog에서 확인해 행별 backfill을 생략했습니다.
- event 종료 후 별도 보상을 지급해 정상 CLAIM과 CS 보상이 동시에 반영되는 상황을 막았습니다.
- `(event_id, incident_reference, user_id)`와 request ID 제약으로 같은 장애 대상의 중복 보상을 방어하도록 했습니다.

## DBA 직무와 연결되는 내용

이 사례는 테이블·프로시저 버전 관리뿐 아니라 검수와 패치 순서를 보여줍니다. 적용 전에는 구 API 의존성과 기존 데이터 조건을 확인했고, 실패 시 Flyway 이력과 catalog를 대조한 뒤 forward fix를 적용했습니다. 지급 결과는 API 응답, grant, wallet, 출처별 ledger를 각각 대조했습니다.
