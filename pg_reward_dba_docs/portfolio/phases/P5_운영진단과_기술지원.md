# P5 | 운영 진단과 기술 지원

## 한 줄 요약

PostgreSQL의 세션 상태와 blocker 관계를 읽어 오래 열린 트랜잭션이 만든 Lock Wait를 진단하고, 대기 해소 후 요청 처리와 fixture 복구를 확인했습니다.

## 실습 환경

P5 전용 PostgreSQL 17.12 인스턴스 `rewardp5db`와 합성 테이블 한 행을 사용했습니다. 관측 계정 `reward_observer`는 `pg_monitor`와 fixture SELECT 권한을 가졌고 UPDATE 권한은 없었습니다. 앱의 사용자·지급 데이터와 분리해 세션 진단만 반복할 수 있도록 구성했습니다.

관리형 Colima 환경에서 host의 `127.0.0.1:55434` 접속은 응답하지 않았습니다. 확인된 Docker Engine 경로의 `docker exec`로 SQL과 실습 도구를 실행했습니다. 접속 경로를 먼저 검증해 다른 Docker 엔진이나 DB를 보고 측정하는 일을 방지했습니다.

## 장애 재현과 진단 과정

| 단계 | 세션과 관측 | 의미 |
|---|---|---|
| A | PID 507이 `SELECT ... FOR UPDATE` 후 `idle in transaction` | 행 잠금을 보유한 채 트랜잭션이 열린 상태 |
| B | PID 529의 UPDATE가 `Lock/transactionid` 대기 | 대기 세션과 lock wait event 확인 |
| blocker 조회 | `pg_blocking_pids()`가 B의 blocker로 A PID 507을 반환 | SQL·상태·대기 관계를 동일 snapshot에서 연결 |
| C | 별도 SELECT가 balance 100을 44.823ms에 반환 | 쓰기 UPDATE의 대기와 일반 SELECT 동작을 구분 |

waiter만 확인하지 않고 blocker PID와 해당 세션의 SQL, 상태, 트랜잭션 나이를 조회했습니다. 원인이 같은 행의 잠금 자체인지, 장기 열린 트랜잭션인지 구분할 수 있도록 `pg_stat_activity`, `pg_blocking_pids()`, `pg_locks`를 함께 사용했습니다.

## 조치와 복구 확인

실습 세션 A는 업무 데이터를 변경하지 않고 합성 행의 Lock만 보유했으므로 A를 COMMIT했습니다. B는 대기에서 풀려 UPDATE를 완료했고, balance는 100에서 101로 바뀌었습니다. harness가 이를 확인한 뒤 fixture를 기준값 100으로 복구했습니다. 종료 후 observer 조회에서 Lock Wait와 실습 테이블 Lock은 각각 0행이었으며 harness 결과는 `PASS blocker_identified waiter_recovered fixture_restored`였습니다.

## 기술 지원 관점의 설명

같은 증상을 전달받으면 먼저 지연 중인 SQL과 DB 세션을 연결하고, blocker의 상태·트랜잭션 나이·잠금 범위를 확인합니다. 이 실습에서는 원인이 `idle in transaction` 상태인 세션 A로 좁혀졌습니다. 조치 뒤에는 UPDATE 완료, 잔액 결과, 대기 제거, 기준 데이터 복구까지 한 흐름으로 공유할 수 있었습니다.

예시 공유 내용:

> UPDATE가 `Lock/transactionid`에서 대기했습니다. blocker는 행 잠금을 가진 채 `idle in transaction`으로 남아 있던 세션 A였습니다. A의 COMMIT 뒤 UPDATE가 완료됐고, balance와 실습 데이터 복구를 확인했습니다.

실제 운영 시스템에서 blocker를 조치할 때는 세션을 종료하기 전에 SQL과 트랜잭션이 수행 중인 업무를 확인해야 합니다. 이 프로젝트의 재현 환경에서는 데이터 변경 없이 Lock을 만든 합성 세션임을 확인한 뒤 COMMIT했습니다.

## 다음 운영 진단 개선 후보

이번 실습은 SQL 세션 단위 진단에 초점을 뒀습니다. 실제 서비스의 운영 진단으로 확장할 때는 앱 연결의 `application_name`에 요청 식별 정보를 전달하고, DB 세션과 API 요청을 연결하는 기록을 추가할 수 있습니다. 또한 Lock 대기 건수와 `idle in transaction` 지속 시간을 서비스 트랜잭션 기준에 맞춰 관찰하고, 감지·조치·복구 확인 시각을 incident 기록에 남기는 작업이 후속 항목입니다.

## DBA 직무와 연결되는 내용

이 사례는 운영 장애를 재현하고, waiter·blocker 관계를 SQL로 진단한 뒤, 조치 결과를 데이터와 세션 상태로 검증한 과정을 보여줍니다. 현상과 원인, 판단 근거, 조치, 잔여 상태를 구분해 기록해 다른 담당자에게 전달할 수 있는 형태로 정리했습니다.
