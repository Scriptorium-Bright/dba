# P0~P1 구현 기록

**작성 시점:** 2026-11-22  
**상태:** P0~P1 구현과 당시 확인 범위를 기록한다. 전체 TC-001~016 및 P1 UI 흐름은 아직 전부 검증하지 않았다.  
**사전 계획:** [plan.md](../plan.md)

## 추가한 것

### P0 — DB와 실행 기반

- `compose.yaml`: PostgreSQL 17.12와 Spring Boot API를 실행한다. DB/API 포트는 `127.0.0.1`에만 바인딩하고 DB 볼륨을 유지한다.
- `experiments/README.md`: 향후 실험 자료의 위치를 만들고 아직 측정/자동화 결과가 없음을 명시한다.
- `database/bootstrap/10-create-roles.sh`: `reward_app`, `reward_migration`, `reward_observer`를 만들고 각각 DML, DDL, 읽기 역할을 분리한다.
- `database/migrations/V1__create_reward_schema.sql`: 사용자·지갑·이벤트·대상자·지급·원장·감사·배치 테이블, 제약과 조회 인덱스를 추가한다.
- `database/migrations/V2__seed_demo_data.sql`: 데모 사용자 3명, CLAIM 이벤트, 대상자 3명이 사전 등록된 DRAFT BATCH 이벤트를 추가한다.
- Spring Boot 3.5.16 / Java 21 API, Flyway 별도 접속 계정, Actuator health 설정을 추가한다.
- `.env.example`, `.gitignore`, 루트 `README.md`와 정확한 프런트 패키지 버전의 `package-lock.json`을 추가했다.
- `.dockerignore`로 프런트 의존성·문서·로컬 빌드 파일을 API 이미지 빌드 컨텍스트에서 제외했다.

### P1 — 이벤트·지갑·운영 UI

- React 19.3.1 + Vite 8.3.8 화면에서 이벤트 목록/상세, 상태·지급 방식·예약 시각·대상 수, Money·Point 보상, 지갑·최근 원장을 표시한다.
- 개발용 사용자 101~103 전환과 사용자/운영자 역할 전환을 제공한다.
- 운영자는 이벤트를 DRAFT로 만들고 DRAFT→OPEN→CLOSED 상태 전이를 실행한다. 이벤트 상태 감사 행을 같은 트랜잭션에서 기록한다.
- 사용자는 CLAIM 이벤트를 수령할 수 있다. API 트랜잭션 안에서 `reward_grants`, `wallets`, `wallet_ledger`를 갱신하며 같은 `Idempotency-Key` 재시도, 이미 지급된 결과, 수령 불가를 구분한다.
- 네트워크 오류 뒤에는 브라우저가 같은 사용자·이벤트 요청 ID를 유지해 결과를 다시 확인한다.
- BATCH 예약 시각과 대상 수는 표시한다. 대상자 없는 BATCH 이벤트는 오픈하지 못하게 해 대상 명단 확정 전에 지급 상태가 열리는 것을 막는다.

## 추가·변경 이유

| 변경 | 이유 |
|---|---|
| `event_status_audit` 테이블 | BF-03은 상태 변경 이력을 요구하지만 기준 스키마에는 보상 정책 변경 감사만 있었다. 두 이력을 별도 테이블에 저장한다. |
| P1 지급 트랜잭션을 Spring 서비스에 구현 | Phase 문서가 P1에는 초기 수령 API, P2에는 지급 SP 확정을 둔다. P1 범위에서 화면과 실제 DB 상태를 연결하되 SP/배치 작업은 앞당기지 않았다. |
| BATCH 데모 대상 3명을 DRAFT 이벤트에 미리 등록 | 운영 규칙의 “OPEN 전에 대상 확정”을 지키고, 대상 등록 기능이 P2라는 범위도 유지한다. |
| API·Flyway 계정 분리 | 런타임 API가 DDL 권한을 갖지 않도록 한다. |
| 요청 결과 `REPLAYED`/`ALREADY_GRANTED`/`NOT_AVAILABLE` 분리 | UI에서 재시도·기지급·수령 불가를 사용자가 구분할 수 있게 한다. |
| 인증 대신 명시적 로컬 데모 역할 전환 | 실제 인증 제품화는 문서의 제외 범위다. 따라서 UI 기능 확인용이며 운영 권한으로 사용할 수 없도록 로컬 바인딩과 함께 설명했다. |

## 실행 및 검증 상태

- 2026-11-22 로컬 서버를 시작했다. Docker 이미지 빌드 성공, PostgreSQL 17.12 healthy, Flyway 2개 migration 적용, API health `UP`, 프런트 HTTP 200과 `/api/events` 응답을 확인했다.
- 테스트를 추가하거나 기능 테스트를 실행하지 않았다. CLAIM 지급·운영자 상태 변경은 브라우저에서 아직 검증하지 않았으므로 P0/P1 전체 Gate는 미완료다.
- 패키지 잠금 파일은 `npm install --package-lock-only --ignore-scripts --no-audit --no-fund`로 만들었고, 이후 `npm ci`로 프런트 의존성을 설치했다.
- 기본 5173, 8080, 8081 포트는 기존 Node 프로세스가 사용 중이라 프런트 5174, API 8082를 선택했다. PostgreSQL은 5432다. 포트 충돌이 나면 기존 프로세스를 종료하지 않고 다른 포트를 사용한다.
- Docker Desktop 앱이 열리지 않아 Colima를 임시 경로에서 시작했다. Compose 데이터는 named volume에 저장된다.
- 작업 디렉터리에 Git 저장소 메타데이터가 없어 Git diff/커밋은 만들지 않았다.

## 남은 검증과 범위

- 사용자 수령과 운영자 상태 전이의 end-to-end 흐름, UI의 에러/미확정 상태는 별도로 확인해야 한다.
- CLAIM 성공 후 지급 스냅샷, Money/Point 잔액, 각 원장 행이 일치하는지 실제 PostgreSQL에서 확인해야 한다.
- OPEN/CLOSED 상태 전이와 감사 행, BATCH 대상 유무에 따른 OPEN 거부도 확인해야 한다.
- P2 저장 프로시저 전환, 동시 요청 측정, 100개 요청 검증, BATCH 작업자·중단/재실행은 구현하지 않았다.
- 사용자·운영자 헤더는 데모용이다. 실제 인증이나 서비스 배포에 사용하면 안 된다.
