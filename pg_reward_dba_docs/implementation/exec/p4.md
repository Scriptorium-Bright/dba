## 0단계 — P4 환경과 실행 범위

- P4는 Compose project `reward-p4`, DB `rewardp4db`, volume `reward_p4_pgdata`를 사용합니다.
- P4 API는 8282, DB는 55433, 화면은 5176입니다. P2의 8082/5432/5174와 P3의 8182/55432/5175는 유지했습니다.
- P4 API의 검색 인덱스는 P4 전용 Flyway V15이며, 공용 지급 요청 UUID 변경은 V16입니다. 인덱스와 workload fixture는 P4 전용 DB/location에 둡니다.
- API 관리자 조회는 `GET /api/admin/payouts`입니다. `sourceType`, `userId`, `from`, `to`, `beforeId`, `limit` 조건을 받습니다.
- 새 P4 DB는 공용 V1–V14, P4 전용 V15, 공용 V16을 적용합니다. V15는 fixture를 넣기 전에 빈 원장에 세 인덱스를 concurrent build하며, `flyway_schema_history`에 버전을 기록합니다. pre-index 계획을 재현할 때는 fixture 적재 뒤 전용 helper로 인덱스를 내립니다.

## 2단계 — fixture 구성과 데이터 대사

첫 적재에서 compensation timestamp 계산이 너무 최신 쪽으로 치우친 분포를 만들었습니다. 그 fixture는 제거하고 식을 `n * 99 + 49`로 조정해 COMPENSATION 한 행을 약 99개 EVENT 행마다 배치했습니다. 재생성은 P4 전용 `reward_p4_pgdata`에만 했습니다. 조정 뒤 최신순 필터도 보상 행을 여러 번 건너뛰어야 하므로 cursor 인덱스 기준선이 더 잘 드러납니다.

| 확인 | 결과 |
|---|---:|
| EVENT ledger | 990,000 |
| COMPENSATION ledger | 10,000 |
| EVENT grant | 990,000 |
| COMPENSATION record | 10,000 |
| fixture 사용자 wallet/ledger 불일치 | 0명 |

seed 직후 `VACUUM (ANALYZE)`와 테이블 통계 갱신을 실행했습니다.

| 최신순 100건 | `wallet_ledger_pkey` backward scan + source filter | 결과 100건을 얻기 전 `Rows Removed by Filter: 9851`, 2.148ms, shared buffer hit 429/read 34 |

## 4단계 — SQL 분기 가설과 결정

처음에는 `sourceType`에 따라 EVENT/COMPENSATION JOIN을 따로 구성하는 SQL을 비교했습니다. COMPENSATION 전역 조회는 `wallet_ledger_compensation_id_idx`에서 보상 10,000행을 읽은 뒤 정렬했고 15.562ms였습니다. 날짜 조회는 같은 10,000행을 읽어 9,912행을 filter에서 제외한 뒤 7.662ms에 완료했습니다.

제품 조회는 공통 JOIN과 projection을 유지하고, 검증된 source literal을 WHERE 조건에 넣습니다. 이 query shape에서 PostgreSQL은 부분 인덱스로 최신 100행을 찾고 날짜 조건에 해당하는 ledger 후보만 읽었습니다.

## 5단계 — 인덱스 후보 비교와 최종 반영

전체 출처 인덱스 후보 `(source_type,id DESC)`는 약 30MB였고 전역 검색은 0.703ms였습니다. 첫 partial index 후보에는 응답 payload를 `INCLUDE`로 넣었지만, 최종 선택 전 실행계획과 payload 없는 후보를 다시 비교했습니다. COMPENSATION을 명시한 검색에 선택된 인덱스 이름은 다음과 같습니다.

1. `wallet_ledger_compensation_cursor_idx`: `id DESC`, `WHERE source_type='COMPENSATION'`.
2. `wallet_ledger_compensation_created_idx`: `created_at DESC, id DESC`, 같은 partial predicate.

sourceType을 생략한 기간 검색에는 `wallet_ledger_any_source_created_idx` `(created_at DESC, id DESC)`를 별도로 선택했습니다. 이 인덱스는 두 출처를 모두 포함하며 최종 실제 크기는 31,522,816 bytes입니다. 전체 `(source_type,id DESC)`는 검색 키 순서를 비교한 초기 후보입니다.

첫 INCLUDE 정의는 688,128 bytes씩이었습니다. 이 plan은 두 검색 모두 `Index Scan`이었고 index-only scan이 아니었습니다. query projection의 `reward_grant_id`는 INCLUDE 목록에 없었으며, 같은 query를 payload 없는 후보로 실행해도 P4 ledger child buffer는 cursor 102, date 90으로 기존과 같았습니다. 같은 P4 table에서 key-only 후보는 cursor 245,760 bytes, date 335,872 bytes였고 planner는 실제 두 검색에서 후보를 선택했습니다. 따라서 INCLUDE가 이 workload에서 heap access를 줄였다는 결과는 없었습니다.

6컬럼 사전 probe는 날짜 인덱스 추가 WAL 4,839,500 bytes, PK-only WAL 8,061,500 bytes를 기록했습니다. 최종 비교는 [canonical 8컬럼 SQL](../../../experiments/sql/p4_write_cost.sql)로 같은 50,000행을 네 구성에 적재했습니다. PK-only WAL은 8,857,500 bytes, INCLUDE indexes는 9,010,900 bytes, key-only indexes는 8,938,060 bytes, all-source date index는 13,697,000 bytes였습니다. key-only 선택으로 compensation partial index의 추가 WAL은 153,400에서 80,560 bytes로 줄었고, scratch index 크기는 80+80KB에서 48+40KB로 줄었습니다. 전체 date index의 추가 WAL 4,839,500 bytes는 같은 폭의 PK-only 대비 54.64%였습니다. 이 결과에 따라 최종 partial indexes에서 INCLUDE payload를 제외하고 세 인덱스를 concurrent build했습니다. 최종 catalog는 compensation partial indexes 각각 245,760/335,872 bytes, all-source date index 31,522,816 bytes이며 세 인덱스 모두 `indisready=t`, `indisvalid=t`입니다.

COMPENSATION 날짜 조회는 `created_at` 범위에서 후보 88행을 찾은 뒤 `Sort Key: l.id DESC` quicksort(47KB)를 실행했습니다. partial created_at 인덱스는 해당 출처의 기간 후보 행을 줄이는 역할을 합니다.

2026-11-23 key-only final plan 재확인은 전역 100건 0.569ms/shared hit 404, 기간 88건 3.043ms/shared hit 462였습니다. INCLUDE 정의 재확인은 각각 0.432ms와 0.210ms였습니다. 각 값은 실행 순서와 cache 상태를 함께 기록한 단일 `EXPLAIN (ANALYZE, BUFFERS)` 관측입니다. 최종 plan은 전역 ID cursor Index Scan, 날짜 created_at Index Scan 후 88행 Sort를 사용했습니다. raw plan과 catalog를 함께 보존했습니다.

### `sourceType`을 생략한 기간 검색

`AdminPayoutController`와 `RewardService.searchPayouts`의 `sourceType`은 선택 파라미터입니다. 두 출처를 함께 검색하는 기간 경로는 [미지정 출처 SQL](../../../experiments/sql/p4_explain_payout_search_any_source.sql)로 따로 측정했습니다.

최근 2026-11-07~09 요청은 ID와 timestamp가 함께 증가하는 fixture에서 PK 역방향 스캔으로 100행을 찾았습니다. 동일 role assertion이 있는 raw plan은 인덱스 전 0.380ms/shared buffers 408, 인덱스 후 1.106ms/shared buffers 408을 기록했습니다. 과거 2026-06-01 30분 요청은 1,000,000행 Parallel Seq Scan에서 worker 합계 999,870행을 filter하고 130행을 반환했습니다. 최신 `reward_app` role assertion 실행은 95.029ms/shared buffers hit 11,105였습니다.

비부분 `(created_at DESC, id DESC)` 인덱스 추가 후 과거 조회는 날짜 인덱스에서 130행을 읽고 `id DESC` sort를 수행했습니다. 최종 `reward_app` role assertion `EXPLAIN ANALYZE`는 4.394ms/shared buffers hit 980이었습니다. API 전후 응답은 각각 HTTP 200, 100행(99 EVENT/1 COMPENSATION), id 130부터 31까지였습니다. 실행 계획은 전체 순차 스캔에서 조건부 Index Scan으로 바뀌었고 buffer hit는 11,105에서 980으로 줄었습니다.

같은 SQL을 API의 bind parameter 형태로 `PREPARE`/`EXPLAIN EXECUTE` 했을 때도 날짜 인덱스를 선택하고 130행 뒤 `id DESC` sort를 수행했습니다(2.715ms, shared hit 977). 실행계획 표본은 [sourceType 생략 계획 결과](../../../experiments/results/p4_unfiltered_period_plans_with_all_source_index_2026-11-23.txt)에 있습니다.

### `userId`와 기간을 함께 지정한 관리자 검색

선택적인 `userId`, `from`, `to`를 동시에 제공하는 실제 관리자 검색 SQL을 100만 행 fixture에서 `reward_app` 로그인으로 확인했습니다. 최근 이틀 구간(user 110000)은 `(user_id,id DESC)` 인덱스에서 100 TID, all-source 날짜 인덱스에서 8,830 TID를 읽고 bitmap 교집합 2행·heap 2 block을 반환했습니다. 과거 30분 구간(user 100001)은 두 인덱스에서 100/130 TID를 읽고 2행·heap 1 block을 반환했습니다. 두 계획 모두 `Rows Removed by Filter` 없이 두 인덱스의 BitmapAnd를 사용했습니다.

같은 prepared query를 다섯 번 실행했을 때 `generic_plans=0/custom_plans=5`였습니다. 6·7번째 AUTO 계획은 generic으로 전환되어 `generic_plans=2/custom_plans=5`였고 두 날짜 구간에서 같은 BitmapAnd 경로를 선택했습니다. forced generic 계획도 같은 인덱스 조합을 사용했으며 최근/과거 buffers는 52/19였습니다. 최근과 과거는 각각 한 번 측정한 표본입니다. 현재 복합 인덱스 조합이 이 fixture의 검색 조건을 해결하므로 추가 `(user_id, created_at, id)` 인덱스를 반영하지 않았습니다.

### Prepared statement 계획 선택 확인

P4 connection URL에는 pgJDBC `prepareThreshold` override가 없습니다. 공식 pgJDBC 설정에서 기본값은 같은 `PreparedStatement`의 다섯 번째 실행부터 server-side prepared statement를 사용하며, query cache는 각 connection에 따로 존재합니다. PostgreSQL `plan_cache_mode=auto`는 첫 다섯 실행의 custom-plan 비용을 generic-plan 비용과 비교합니다. 이를 확인하려고 동일 parameterized query를 한 reward_app 세션에서 최근·과거 범위로 번갈아 실행했습니다. 다섯 실행 뒤 `pg_prepared_statements`는 `generic_plans=0, custom_plans=5`였고, EXPLAIN EXECUTE 두 번 뒤에도 `generic_plans=0, custom_plans=7`이었습니다. 최근 범위는 primary-key 역방향 계획, 과거 범위는 all-source date Index Scan을 선택했습니다.

`force_generic_plan`으로 실행한 두 범위는 같은 `Parallel Index Scan Backward using wallet_ledger_pkey` 계획을 사용했습니다. 최근 범위는 5.712ms/buffers 2,518, 과거 범위는 worker당 `Rows Removed by Filter: 333,290`, 147.159ms/buffers 18,665였습니다. 이 세션은 `generic_plans=2, custom_plans=0`을 기록했습니다. AUTO 모드의 동일 parameterized query는 `generic_plans=0, custom_plans=7`이었고, 최근 범위는 primary-key 역방향 계획, 과거 범위는 all-source date Index Scan을 선택했습니다.

실험은 SQL shape와 API DB role `reward_app`을 assertion으로 확인하고 `psql PREPARE`로 실행했습니다. `pg_prepared_statements`는 현재 세션의 generic/custom plan counters를 보여줍니다. pgJDBC는 connection별 query cache와 기본 `prepareThreshold`를 사용합니다. 관련 규칙은 [PostgreSQL 17 PREPARE 문서](https://www.postgresql.org/docs/17/sql-prepare.html)와 [pgJDBC connection parameters](https://jdbc.postgresql.org/documentation/use/#connection-parameters)에 정리돼 있습니다.

이 전체 날짜 인덱스의 catalog 크기는 31,522,816 bytes(약 30 MiB)입니다. 같은 50,000행과 동일 컬럼을 넣은 [네 구성 WAL 비교](../../../experiments/results/p4_write_cost_all_candidates_2026-11-23.txt)에서 PK-only는 8,857,500 bytes, 전체 날짜 인덱스는 13,697,000 bytes를 기록했습니다. 추가 WAL 4,839,500 bytes(54.64%)는 보상 1% partial key-only 인덱스의 80,560 bytes(0.91%)보다 큽니다. 임시 전체 날짜 인덱스는 약 2,760KB였고, 실제 100만 행 인덱스는 약 30 MiB입니다.

관리자 API의 출처 생략 기간 검색은 비부분 날짜 인덱스로 지원합니다. 같은 50,000행 fixture에서 추가 WAL 4,839,500 bytes와 실제 100만 행 인덱스 31,522,816 bytes를 기록했습니다. `sourceType=COMPENSATION` 검색은 보상 전용 partial indexes를 선택했고, 일반 최신순 검색은 정렬된 primary-key 경로를 사용했습니다.

## 7단계 — CREATE INDEX와 CONCURRENTLY

`python3 experiments/p4_index_build_demo.py` 실행 결과입니다. UPDATE는 amount 값을 그대로 다시 쓰는 no-op 작업이며 최종 잔액·원장값은 바꾸지 않습니다.

| 단계 | 실행·관측 |
|---|---|
| A | DML transaction이 `RowExclusiveLock`을 잡고 `pg_sleep(25)` 대기 |
| B | 일반 `CREATE INDEX`가 relation lock에서 대기. `lock_timeout=8s` 후 8.07초에 실패 |
| C | B가 lock queue에 선 뒤 시작한 UPDATE도 relation lock에서 대기. B timeout 후 약 8.02초에 재개되어 A 종료 전 완료 |
| normal 재시도 | A 종료 뒤 일반 index build 성공, 0.593초 |
| A2/B2 | `CREATE INDEX CONCURRENTLY` 중 기존 transaction의 `virtualxid` 종료를 기다림 |
| C2 | concurrent build 중 UPDATE 성공, 0.045초 |
| 완료 | A2 종료 뒤 concurrent build 성공, 전체 25.691초, `indisready=true`, `indisvalid=true` |

이 비교에서 normal DDL은 lock queue 뒤의 UPDATE도 기다리게 했습니다. CONCURRENTLY는 A2 종료를 기다리는 동안 일반 DML C2를 완료했습니다. 비교용 probe index는 스크립트의 `finally`에서 제거됩니다.

### Flyway 자동 적용과 새 DB 확인

P4 전용 migration location에 V15를 추가하고, `compose.p4.yaml`에서 `SPRING_FLYWAY_POSTGRESQL_TRANSACTIONAL_LOCK=false`를 설정했습니다. migration 파일의 companion `.conf`는 `executeInTransaction=false`로 둡니다. 초기 fresh probe에서 Flyway schema-history SELECT 세션과 `Lock/virtualxid` 대기를 관측했고 `pg_blocking_pids()`로 해당 blocker를 확인했습니다. 이 관측에 따라 PostgreSQL advisory lock 설정을 보완했고 Spring Boot 3.5.16/Flyway 11.7.2/PostgreSQL 17.12 조합으로 V1–V15 적용을 완료했습니다.

빈 `rewardp4_flyway_probe` DB에서 V1–V15가 모두 성공했고, V15는 `[non-transactional]`로 실행되어 세 인덱스를 만들었습니다. Flyway 전체 migration 시간은 0.116초였고 API application context가 정상 기동했습니다. schema history는 V15 success, `installed_by=reward_migration`, migration execution 7ms였습니다. catalog에서 세 인덱스 모두 exact definition, `indisready=true`, `indisvalid=true`를 확인했습니다. 빈 table의 인덱스 크기는 각각 8KB였습니다. 기존 `rewardp4db`에서는 동일한 수동 구축 인덱스가 있었고, V15가 `IF NOT EXISTS`로 건너뛴 뒤 정의를 검증하고 version을 기록했습니다. 상세 출력은 [fresh 적용 결과](../../../experiments/results/p4_flyway_fresh_deploy_2026-11-23.txt), 처음 설정이 빠진 시도는 [probe 기록](../../../experiments/results/p4_flyway_concurrent_migration_probe_2026-11-23.txt)에 있습니다.

새 P4 volume은 API 시작 시 공용 V1–V14, P4 V15, 공용 V16을 거쳐 검색 인덱스와 최신 지급 절차를 갖춥니다. P4 전용 location은 P4 migration set에 연결했습니다. 무인덱스 기준선은 fixture 적재 뒤 [baseline helper](../../../experiments/sql/p4_drop_final_indexes_for_baseline.sql)로 세 인덱스를 `DROP INDEX CONCURRENTLY`해 만듭니다. 후보 실험 후 `p4_create_indexes_concurrently.sql`로 인덱스를 복구하고 catalog를 검증합니다. P4 인덱스 실험의 Flyway history는 V15 success로 유지됩니다.

### 공용 migration과 P4 전용 migration의 버전 충돌 정리

P4 Compose는 공용 `db/migration`과 P4 전용 `db/p4-migration`을 함께 읽습니다. 두 경로에 V15가 동시에 있으면 Flyway가 duplicate version으로 검증을 중단합니다. 이미 적용된 P4 concurrent-index V15와 그 checksum을 유지하고, 공용 request UUID 변경을 V16으로 이동했습니다. P3 로컬 DB는 적용된 공통 V15 history를 guard SQL로 V16에 정렬했고, P4 기존 DB는 기존 V15 뒤에 V16을 적용했습니다.

기존 `rewardp4db`는 Flyway 16개 migration을 검증하고 V16을 969ms에 적용한 뒤 API를 기동했습니다. 새 `rewardp4freshdb`는 빈 schema에서 공용 V1–V14, P4 V15 `[non-transactional]`, 공용 V16 순서로 16개를 모두 적용했습니다. 전체 migration execution time은 128ms였고, 세 P4 검색 인덱스는 모두 `indisready=true`, `indisvalid=true`였습니다. 이 결과로 기존 DB upgrade와 새 P4 DB 전체 적용 경로를 함께 확인했습니다.

### V15 실패 이력 복구 재현

비트랜잭션 migration 복구 실습은 Flyway history와 catalog를 함께 조회합니다. disposable `rewardp4_flyway_recovery_probe`에서 V14까지 적용한 뒤, [guarded failure SQL](../../../experiments/sql/p4_prepare_flyway_v15_failure.sql)이 기대 이름의 잘못된 `(id)` 인덱스를 만듭니다. V15 `IF NOT EXISTS`는 기존 이름을 확인하고 마지막 exact-definition 검증을 실행합니다. 이 run은 V15 `success=false`를 남겼고, 두 exact indexes와 한 잘못된 정의가 catalog에 남았습니다.

복구는 catalog에서 정의와 ready/valid flags를 확인하고 잘못된 인덱스 하나를 `DROP INDEX CONCURRENTLY`로 제거한 뒤 같은 locations/configuration의 Flyway `repair`, `migrate` 순서로 수행했습니다. 기대 정의가 맞는 인덱스 두 개는 유지했습니다. `repair`는 Flyway 실패 이력을 정리하고 PostgreSQL 객체 상태는 catalog cleanup으로 관리합니다. ### 1,000,000행에서 Flyway V15 적용과 writer 동시 관측

`rewardp4_flyway_populated_probe`에는 V1–V14를 적용한 뒤 P4와 같은 fixture SQL로 EVENT 990,000행과 COMPENSATION 10,000행, 총 1,000,000 ledger를 적재했습니다. migration 직전 harness가 출처별 행 수, wallet-to-ledger mismatch 0건, ledger user의 wallet 누락 0건을 검사하고 JSON에 기록합니다. 첫 두 partial index를 먼저 concurrent build하고 ready/valid 상태를 확인한 뒤 오래된 snapshot을 열었습니다. 이 순서로 V15가 세 번째 `wallet_ledger_any_source_created_idx` 생성 단계까지 진행합니다.

`pg_stat_progress_create_index`에서 target index의 `waiting for old snapshots` 단계를 확인했고, `pg_stat_activity`의 `Lock/virtualxid` waiter PID 72736에 대한 `pg_blocking_pids()`가 snapshot PID 72706을 반환했습니다. 이 대기 중 COMPENSATION ledger id 50의 indexed key `created_at`을 `2026-06-01 00:11:26+00`에서 `2100-01-01 00:00:00+00`으로 갱신했습니다. `UPDATE 1`은 0.075642초에 완료됐습니다. PostgreSQL은 이 컬럼을 인덱스 키로 유지하며, 선택한 행은 앞선 COMPENSATION partial date index와 all-source date index 양쪽에서 갱신됩니다.

snapshot을 종료한 뒤 Flyway는 V15 한 건을 적용했습니다. 목표 시각을 `created_at`으로 조회하면서 `source_type` 조건을 생략하자 `EXPLAIN`은 `wallet_ledger_any_source_created_idx`의 `Index Only Scan`을 선택했고 실제 결과는 같은 id 50이었습니다. 원래 timestamp로 복구한 뒤 최종 timestamp가 일치했습니다. 사후 대사에서 wallet-ledger mismatch 0건과 wallet 없는 원장 사용자 0건을 다시 계산해 확인했습니다.

V15의 세 인덱스는 모두 exact definition, `indisready=true`, `indisvalid=true`였습니다. 원장 100만 행 기준 크기는 cursor 245,760 bytes, compensation-date 335,872 bytes, all-source date 31,522,816 bytes입니다. migration schema history execution time은 1,155ms였고 client 기준 migration 경과는 2.272초였습니다. 자세한 source 분포·사전 인덱스·사후 대사·PID 관계·관측값은 [populated Flyway 결과 JSON](../../../experiments/results/p4_flyway_populated_concurrency_2026-11-23.json)에 있습니다.

## 11단계 — 사용자 원장 조회와 데이터 모델 결정 재검토

`python3 experiments/sql/p4_explain_user_ledger.sql`은 API의 `GET /api/me/ledger?limit=20` first-page 쿼리와 같은 JOIN, `user_id`, `ORDER BY id DESC`, `LIMIT 20`을 실행합니다. fixture에서 user 100001은 EVENT ledger 99행과 COMPENSATION ledger 1행을 가집니다.

| 확인 | 실제 값 |
|---|---|
| API | HTTP 200, 20행, id 989900부터 797981까지 |
| P4 fixture | 전체 ledger 1,000,000행; EVENT 990,000, COMPENSATION 10,000; user 100001 소유권 불일치 0건 |
| 주요 접근 | `wallet_ledger_user_id_id_idx` Index Scan, 조건 `user_id=100001`, id 내림차순 20행 |
| 실행계획 | Nested Loop; grant/compensation/event PK·unique index lookup; 146 shared buffers hit, Planning 0.819ms, Execution 2.656ms |

이 실행은 warm-cache 상태의 단일 `EXPLAIN (ANALYZE, BUFFERS)` 표본입니다. P5 API latency 실습은 100개 client duration의 nearest-rank p95와 동시 요청 중 DB 지표를 별도로 수집합니다.

### 정규화와 의도한 중복

- `wallet_ledger.user_id`는 지급 소유자를 원장에 반복 저장하는 의도된 중복으로, 사용자 원장 검색의 `(user_id, id DESC)` 접근 경로에 사용합니다. EVENT 쪽 `(reward_grant_id, user_id)`, COMPENSATION 쪽 `(compensation_id, user_id)` 복합 FK가 지급 소유자와 ledger 사용자 일치를 강제합니다.
- `wallet_ledger.source_type`은 source FK의 NULL 패턴을 표현하는 중복 구분자입니다. V8 CHECK와 출처별 composite FK가 source type과 출처 참조를 함께 제한하고, P4 API literal 및 partial index predicate에서 공통으로 사용합니다.
- `wallets.money_balance/point_balance`는 원장 합계와 함께 유지하는 현재 잔액 요약입니다. 지급 procedure transaction이 잔액과 ledger를 함께 갱신하며 P2/P3 acceptance와 reset 전 대사가 두 값을 대조합니다.
- `reward_grants`와 `compensations`의 금액은 지급 시점 snapshot으로, 이벤트 정책 변경 뒤에도 당시 지급 값을 보존합니다.
- P4 사용자 원장 조회는 `wallet_ledger_user_id_id_idx`로 필터와 최신순 cursor를 처리했습니다. 100만 행 fixture의 API 응답은 20행, id 989900부터 797981까지였고 plan은 146 shared buffers hit를 기록했습니다.

### 현재 P4 DB migration

V12는 P4의 별도 `rewardp4db`에서도 성공 적용했습니다. V13은 보상 업무 키 중복 시 payload 비교, V14는 로컬 reset helper의 search_path를 고정했습니다. P4-only V15는 세 조회 인덱스를 versioned concurrent DDL로 적용합니다. 공용 V16은 두 지급 프로시저의 request UUID 범위를 맞춥니다. 기존 P4 API는 V16 success 상태로 실행 중이며, 최종 인덱스는 P4 전용 DB/volume에 있습니다.
