## 0단계 — P4 환경과 실행 범위

- P4는 Compose project `reward-p4`, DB `rewardp4db`, volume `reward_p4_pgdata`를 사용합니다.
- P4 API는 8282, DB는 55433, 화면은 5176입니다. P2의 8082/5432/5174와 P3의 8182/55432/5175는 유지했습니다.
- P4 API가 사용하는 schema는 Flyway V11입니다. 성능 측정 전용 인덱스와 workload fixture는 P4 DB에만 생성했습니다.
- API 관리자 조회는 `GET /api/admin/payouts`입니다. `sourceType`, `userId`, `from`, `to`, `beforeId`, `limit` 조건을 받습니다.

## 2단계 — fixture 구성과 데이터 대사

첫 적재에서 compensation timestamp 계산이 너무 최신 쪽으로 치우친 분포를 만들었습니다. 그 fixture는 제거하고 식을 `n * 99 + 49`로 조정해 COMPENSATION 한 행을 약 99개 EVENT 행마다 배치했습니다. 재생성은 P4 전용 `reward_p4_pgdata`에만 했습니다. 조정 뒤 최신순 필터도 보상 행을 여러 번 건너뛰어야 하므로 cursor 인덱스 기준선이 더 잘 드러납니다.

| 확인 | 결과 |
|---|---:|
| EVENT ledger | 990,000 |
| COMPENSATION ledger | 10,000 |
| EVENT grant | 990,000 |
| COMPENSATION record | 10,000 |
| fixture 사용자 wallet/ledger 불일치 | 0명 |

seed 직후 `VACUUM (ANALYZE)`와 테이블 통계 갱신을 실행했습니다.

## 3단계 — 인덱스 전 기준선

관리자 통합 지급 조회 SQL에서 `sourceType=COMPENSATION`으로 검색했습니다.

| 조회 | 기준 실행계획 | 관측 |
|---|---|---|
| 최신순 100건 | `wallet_ledger_pkey` backward scan + source filter | 결과 100건을 얻기 전 `Rows Removed by Filter: 9851`, 2.148ms, shared buffer hit 429/read 34 |
| 2026-11-07~2026-11-09 | `Parallel Seq Scan` + top-N sort | worker별 약 333,304행을 filter에서 제거, shared hit 10,766, 47.817ms |

조회 계획은 [기준 실행 SQL](../../../experiments/sql/p4_explain_payout_search.sql)로 다시 실행할 수 있습니다. 날짜 검색은 1백만 ledger를 훑는 계획이었고, 전역 cursor는 EVENT 행을 반복해서 제외하는 계획이었습니다.

## 4단계 — SQL 분기 가설과 결정

처음에는 `sourceType`에 따라 EVENT/COMPENSATION JOIN을 따로 구성하는 SQL을 시도했습니다. COMPENSATION 전역 조회는 `wallet_ledger_compensation_id_idx`에서 보상 10,000행을 읽은 뒤 정렬했고 15.562ms였습니다. 날짜 조회도 같은 10,000행을 훑고 9,912행을 filter에서 제외해 7.662ms였습니다.

이 계획을 제품 코드에 반영하지 않았습니다. 기존 공통 JOIN을 유지하면 PostgreSQL이 부분 인덱스에서 최신 100행을 바로 찾고, 날짜 조건에서 해당 기간의 ledger만 읽었습니다. 코드 수정은 조회 SQL의 projection과 JOIN 형태가 아닌, 검증된 source literal을 WHERE에 넣는 부분으로 제한했습니다.

## 5단계 — 인덱스 후보 비교와 최종 반영

전체 출처 인덱스 후보 `(source_type,id DESC)`는 약 30MB였고 전역 검색은 0.703ms였습니다. partial cursor 후보는 672KB로 같은 결과를 반환했고, 기간 후보도 672KB였습니다. 최종 인덱스 이름은 다음과 같습니다.

1. `wallet_ledger_compensation_cursor_idx`: `id DESC`, 필요한 ledger 필드 INCLUDE, `WHERE source_type='COMPENSATION'`.
2. `wallet_ledger_compensation_created_idx`: `created_at DESC, id DESC`, 필요한 ledger 필드 INCLUDE, 같은 partial predicate.

두 인덱스는 `p4_create_indexes_concurrently.sql`에서 생성했습니다. catalog 결과 `indisready=t`, `indisvalid=t`이고 각 인덱스 크기는 672KB였습니다. 실행계획은 전역 조회에서 cursor 인덱스, 기간 조회에서 created_at 인덱스를 선택했습니다.

최종 인덱스 재측정은 전역 100건 0.459ms/shared hit 404, 기간 88건 0.242ms/shared hit 533이었습니다. 그 직전 반복에서는 1.136ms와 0.253ms였고, 첫 final 실행은 42.890ms와 4.239ms였습니다. 실행계획은 세 번 모두 cursor/date partial index를 골랐습니다. 실행계획과 buffer 수를 함께 기록했습니다.

## 6단계 — 인덱스 추가 쓰기와 공간 비용

`p4_write_cost.sql`로 같은 50,000행을 PK-only와 partial-index scratch table에 넣었습니다. 데이터 중 1%가 COMPENSATION이며 최종 인덱스 정의를 사용했습니다.

| 측정 | PK-only | 부분 인덱스 2개 추가 |
|---|---:|---:|
| WAL bytes | 8,857,500 | 9,010,900 |
| 추가 WAL | — | 153,400 bytes (약 1.73%) |
| 두 partial index 크기 | — | 각 80KB (fixture 500개 보상행) |

두 실행 시간은 86.729ms와 83.248ms였고 이 차이로 쓰기 지연을 판단하지 않았습니다. 별도 인덱스 크기와 WAL 양으로 추가 비용을 기록했습니다. scratch table은 SQL 파일 마지막에서 제거했습니다.

## 7단계 — CREATE INDEX와 CONCURRENTLY

`python3 experiments/p4_index_build_demo.py` 실행 결과입니다. UPDATE는 amount 값을 그대로 다시 쓰는 no-op 작업이며 최종 잔액·원장값은 바꾸지 않습니다.

| 단계 | 실행·관측 |
|---|---|
| A | DML transaction이 `RowExclusiveLock`을 잡고 `pg_sleep(25)` 대기 |
| B | 일반 `CREATE INDEX`가 relation lock에서 대기. `lock_timeout=8s` 후 8.07초에 실패 |
| C | B가 lock queue에 선 뒤 시작한 UPDATE도 relation lock에서 대기. B timeout 후 약 8.02초에 재개되어 A 종료 전 완료 |
| normal 재시도 | A 종료 뒤 일반 index build 성공, 0.593초 |
| A2/B2 | `CREATE INDEX CONCURRENTLY` 중 기존 transaction의 `virtualxid` 종료를 기다림 |
| C2 | concurrent build 중 UPDATE 성공, 0.045초 |
| 완료 | A2 종료 뒤 concurrent build 성공, 전체 25.691초, `indisready=true`, `indisvalid=true` |

이 비교에서 normal DDL은 lock queue 뒤의 UPDATE도 기다리게 했습니다. CONCURRENTLY는 A2 종료를 기다렸지만 일반 DML C2는 완료했습니다. 비교용 probe index는 스크립트의 `finally`에서 제거됩니다.

## 9단계 — 재실행 순서

P4 server start, UI start, seed, explain, candidate/final index, write-cost와 index-method commands는 [P4 실행 안내](../phase-guide.md#현재-phase-p4--대량-지급-이력-검색과-인덱스-튜닝)에 정리했습니다. seed는 빈 P4 ledger에서 한 번 실행하고, 이미 fixture가 있는 상태에서 다시 실행하면 guard가 중단합니다.

## 10단계 — 판단 요약

| 판단 | 이유 |
|---|---|
| 보상 출처 전용 partial indexes 두 개 | 1% 출처만 색인해 전역 ID cursor와 날짜 조회를 각각 지원하고, 각 인덱스는 672KB였습니다. |
| sourceType 분기 JOIN 제거 | PostgreSQL이 compensation id 인덱스로 10,000행을 읽고 정렬해, 공통 JOIN + source literal보다 느린 계획을 선택했습니다. |
| 검색 파라미터의 source literal 사용 | 값은 EVENT/COMPENSATION으로 검증된 뒤 query에 추가되어 partial predicate가 계획 단계에서 증명됩니다. |
| final indexes를 P4 SQL로 분리 | `CREATE INDEX CONCURRENTLY` 비교와 선택 인덱스 반영을 재현 가능하게 두고, P2/P3 Flyway 경로와 구분합니다. |
| 성능 기록에 계획·buffer·WAL·index size 병기 | 캐시 상태와 실행 환경에 따라 단일 query time이 달라져 구조와 비용 지표도 같이 읽을 수 있습니다. |

P4 UI에서 지급 이력을 검색할 수 있고, P4 SQL과 인덱스 생성 실습의 측정 결과가 이 문서에 이어집니다.
