## 0단계 — 환경과 범위

- P5 프로젝트명 `reward-p5`, DB `rewardp5db`, volume `reward_p5_pgdata`, PostgreSQL `17.12`를 사용했습니다.
- DB 포트는 Docker Engine loopback의 `55434`; 관리형 Colima 세션에서는 같은 엔진의 `docker exec`로 SQL과 harness를 실행했습니다.
- Mac host에서 `127.0.0.1:55434`로 직접 접속한 `pg_isready`는 응답하지 않았습니다. P5 명령은 동작이 확인된 Docker Engine 경로로 실행했습니다.
- Docker Server `29.2.0`, Docker Compose `5.1.4`였습니다.
- P2 `5432`, P3 `55432`, P4 `55433`의 DB와 API 컨테이너는 계속 `Up` 상태였습니다. P5는 새 DB 컨테이너만 추가했습니다.
- P5 실습은 앱의 지급 테이블·사용자 데이터를 쓰지 않습니다. `p5_ops.lock_lab`의 합성 행 하나만 사용합니다.

```sh
export DOCKER_HOST=unix:///private/tmp/reward-colima/active-docker.sock
docker -H "$DOCKER_HOST" compose -p reward-p5 -f compose.p5.yaml up -d
docker -H "$DOCKER_HOST" compose -p reward-p5 -f compose.p5.yaml ps
docker -H "$DOCKER_HOST" exec -i reward-p5-db-1 psql -X -v ON_ERROR_STOP=1 \
  -U reward_bootstrap -d rewardp5db < experiments/sql/p5_prepare_lock_lab.sql
```

컨테이너 상태는 `Up (healthy)`, 이미지 버전은 `17.12 (Debian 17.12-1.pgdg13+1)`였습니다. 준비 SQL은 현재 DB가 `rewardp5db`인지 확인하고 단일 행 `id=1, balance=100`을 만들었습니다.

## 2단계 — 관측 계정과 기준선

observer로 관측 SQL을 실행했습니다. 장애 세션이 없는 기준 시점에서 Lock Wait 결과는 0행이었습니다.

```text
waiter/blocker query: 0 rows
p5_* lock rows:       0 rows
```

observer 권한도 DB에서 확인했습니다.

| 확인 항목 | 결과 |
|---|---|
| DB / PostgreSQL | `rewardp5db` / `17.12 (Debian 17.12-1.pgdg13+1)` |
| fixture balance | `100` |
| fixture SELECT | 허용 (`t`) |
| fixture UPDATE | 거부 (`f`) |
| `pg_monitor` 멤버십 | 허용 (`t`) |

## 3단계 — 장애 재현과 진단

```sh
python3 experiments/p5_lock_incident.py
```

실험은 다음 순서로 진행됐습니다.

1. 세션 A (`p5_blocker_a`, PID `507`)가 `BEGIN` 후 `SELECT ... FOR UPDATE`를 실행했습니다.
2. A는 트랜잭션을 열린 채 두어 `idle in transaction` 상태가 됐습니다.
3. 세션 B (`p5_waiter_b`, PID `529`)가 같은 행을 UPDATE했고 `Lock/transactionid`에서 대기했습니다.
4. observer snapshot에서 B의 Blocker PID `507`, A의 `idle in transaction`, 두 세션의 SQL을 연결했습니다.
5. 세션 C의 SELECT는 B가 대기 중일 때 `balance=100`을 반환했습니다.

실제 출력의 핵심 필드입니다.

```text
database=rewardp5db postgres=17.12 (Debian 17.12-1.pgdg13+1)
blocker_session pid=507 state=idle in transaction xact_age_s=0.164
waiter_session pid=529 state=active wait=Lock/transactionid
blocker_chain=...|529|p5_waiter_b|active|Lock|transactionid|507|p5_blocker_a|idle in transaction|0.435|SELECT ... FOR UPDATE;|UPDATE ...
concurrent_select value=100 elapsed_ms=44.823 while_update_waits=true
```

## 4단계 — 조치, 복구, 재검증

이 fixture에서 A는 값을 바꾸지 않고 Lock만 보유했으므로 A를 COMMIT했습니다. B는 대기에서 풀려 UPDATE를 마쳤습니다.

| 관측 | 결과 |
|---|---|
| A 조치 | `COMMIT`, host UTC `2026-11-22T13:29:42.903912+00:00` |
| B 상태 | `idle`로 복귀, 단조 시계 기준 대기 구간 `0.372s` |
| B 결과 | balance `100 → 101` 한 번 반영 |
| fixture cleanup | balance `100` 복원 |
| 종료 후 Lock Wait/`p5_*` Lock | observer SQL 결과 각각 0행 |
| incident harness | `PASS blocker_identified waiter_recovered fixture_restored` |

PostgreSQL snapshot의 UTC 표시는 `13:29:42.912861`, Python host 시각은 A COMMIT `13:29:42.903912`였습니다. 세션 간 표시 시각은 약 9ms 차이가 있어 순서·대기 시간은 harness의 실행 순서와 단조 시계 측정으로 판단했습니다.

## 5단계 — 원인 판단과 운영 후속 조치

**원인:** A가 행을 잠근 뒤 트랜잭션을 끝내지 않았습니다. B의 UPDATE는 A의 트랜잭션 종료를 기다렸고, PostgreSQL에서는 이 행 Lock 대기가 `Lock/transactionid`로 나타났습니다. C의 일반 SELECT는 이전 committed 버전 `100`을 읽어 같은 행을 쓰려는 UPDATE와 대기 동작이 달랐습니다.

**조치 판단:** 실습 세션 A의 SQL과 상태를 확인하고 COMMIT했습니다. blocker가 실제 업무 변경을 포함한다면 해당 트랜잭션의 작업 내용·영향 범위를 조회해 완료, rollback 또는 취소 조치를 결정하는 절차를 런북에 연결할 수 있습니다.

**기술 지원 공유용 요약:** “P5 진단 DB에서 UPDATE가 `Lock/transactionid` 대기에 들어갔습니다. 원인은 행 Lock을 가진 채 `idle in transaction`인 세션 A였습니다. A를 COMMIT한 뒤 UPDATE가 완료됐고, 잔액 대사와 fixture 복구까지 확인했습니다.”

**후속 운영 개선 후보:**

- 실제 앱 연결의 `application_name`에 서비스·작업 식별 정보를 넣어 SQL 세션과 요청을 연결합니다.
- `idle in transaction`의 지속 시간과 `Lock` 대기 건수를 같이 감시하고, 서비스 트랜잭션 기준에서 알림 임계값을 정합니다.
- 장기 blocker 조치 전에는 대상 PID의 SQL·트랜잭션 나이·잠금 범위·영향 요청을 기록합니다.
- incident 기록에 감지·판단·조치·복구 확인 시각을 따로 남겨 응답 구간을 설명할 수 있게 합니다.

## 6단계 — 재실행 순서

P5 인스턴스가 켜져 있으면 준비 SQL과 harness를 다시 실행합니다. harness는 fixture가 100인지 먼저 확인하고, 실습 종료 시 다시 100으로 복원합니다.

```sh
export DOCKER_HOST=unix:///private/tmp/reward-colima/active-docker.sock
docker -H "$DOCKER_HOST" exec -i reward-p5-db-1 psql -X -v ON_ERROR_STOP=1 \
  -U reward_bootstrap -d rewardp5db < experiments/sql/p5_prepare_lock_lab.sql
python3 experiments/p5_lock_incident.py
docker -H "$DOCKER_HOST" exec -i reward-p5-db-1 psql -X -v ON_ERROR_STOP=1 \
  -U reward_observer -d rewardp5db < experiments/sql/p5_observe_lock_wait.sql
```

P5 DB container는 작업 종료 후에도 healthy 상태와 `reward_p5_pgdata`를 유지하도록 두었습니다. Compose의 `down`은 컨테이너만 내리고, named volume은 `down -v`를 사용하지 않는 한 보존됩니다.
