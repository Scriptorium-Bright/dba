## 3단계 — 장애 재현과 진단

```sh
python3 experiments/p5_lock_incident.py
```

실험은 다음 순서로 진행됐습니다.

1. 세션 A (`p5_blocker_a`, PID `507`)가 `BEGIN` 후 `SELECT ... FOR UPDATE`를 실행했습니다.
2. A는 트랜잭션을 열린 채 두어 `idle in transaction` 상태가 됐습니다.
3. 세션 B (`p5_waiter_b`, PID `529`)가 같은 행을 UPDATE했고 `Lock/transactionid`에서 대기했습니다.
4. observer snapshot에서 B의 Blocker PID `507`, A의 `idle in transaction`, 두 세션의 SQL을 연결했습니다.
5. 세션 C의 SELECT는 B가 대기 중일 때 `balance=100`을 반환했습니다.

실제 출력의 핵심 필드입니다.

```text
database=rewardp5db postgres=17.12 (Debian 17.12-1.pgdg13+1)
blocker_session pid=507 state=idle in transaction xact_age_s=0.164
waiter_session pid=529 state=active wait=Lock/transactionid
blocker_chain=...|529|p5_waiter_b|active|Lock|transactionid|507|p5_blocker_a|idle in transaction|0.435|SELECT ... FOR UPDATE;|UPDATE ...
concurrent_select value=100 elapsed_ms=44.823 while_update_waits=true
```

## 4단계 — 조치, 복구, 재검증

이 fixture에서 A는 값을 바꾸지 않고 Lock만 보유했으므로 A를 COMMIT했습니다. B는 대기에서 풀려 UPDATE를 마쳤습니다.

| 관측 | 결과 |
|---|---|
| A 조치 | `COMMIT` command tag 확인, client 요청 `2026-11-22T18:22:06.211866Z`, psql exit 0 및 tag 확인 `18:22:06.216906Z` |
| B 상태 | `idle` 복귀 확인, client request-to-idle 관측 `0.203s` (send·실행·poll 포함, 순수 DB Lock 시간 아님) |
| B 결과 | `UPDATE 1` command tag와 psql exit 0 확인, balance `100 → 101` 한 번 반영 |
| fixture cleanup | balance `100` 복원 |
| 종료 후 Lock Wait/`p5_*` Lock | observer SQL 결과 각각 0행 |
| incident harness | `PASS blocker_identified waiter_recovered fixture_restored` |

최신 재실행은 `incident_started_utc=2026-11-22T18:22:06.003366+00:00`에 시작했습니다. observer snapshot의 SQL은 blocker의 `SELECT ... FOR UPDATE`와 waiter의 UPDATE를 동시에 확인했고 `pg_blocking_pids()` PID가 각각 `23339 → 23353`으로 연결됐습니다. host UTC는 `18:22:06.188015`, client COMMIT 요청은 `18:22:06.211866`, 확인은 `18:22:06.216906`이었습니다. 이 시각은 DB commit timestamp가 아니라 client 명령 전송·완료 관측 시각입니다.

이 단일 Lock incident는 `experiments/p5_lock_incident.py`의 별도 실행 기록입니다. API latency canonical JSON의 25라운드/100-request Lock scenario와 다른 실행이며, PID·시각·47.237ms SELECT 결과를 두 실행 간 합산하지 않습니다.

## 5단계 — 원인 판단과 운영 후속 조치

**원인:** A가 행을 잠근 뒤 트랜잭션을 끝내지 않았습니다. B의 UPDATE는 A의 트랜잭션 종료를 기다렸고, PostgreSQL에서는 이 행 Lock 대기가 `Lock/transactionid`로 나타났습니다. C의 일반 SELECT는 이전 committed 버전 `100`을 읽어 같은 행을 쓰려는 UPDATE와 대기 동작이 달랐습니다.

**조치 판단:** 실습 세션 A의 SQL과 상태를 확인하고 COMMIT했습니다. blocker가 실제 업무 변경을 포함한다면 해당 트랜잭션의 작업 내용·영향 범위를 조회해 완료, rollback 또는 취소 조치를 결정하는 절차를 런북에 연결할 수 있습니다.

**기술 지원 공유용 요약:** “P5 진단 DB에서 UPDATE가 `Lock/transactionid` 대기에 들어갔습니다. 원인은 행 Lock을 가진 채 `idle in transaction`인 세션 A였습니다. A를 COMMIT한 뒤 UPDATE가 완료됐고, 잔액 대사와 fixture 복구까지 확인했습니다.”

**후속 운영 개선 후보:**

- 실제 앱 연결의 `application_name`에 서비스·작업 식별 정보를 넣어 SQL 세션과 요청을 연결합니다.
- `idle in transaction`의 지속 시간과 `Lock` 대기 건수를 같이 감시하고, 서비스 트랜잭션 기준에서 알림 임계값을 정합니다.
- 장기 blocker 조치 전에는 대상 PID의 SQL·트랜잭션 나이·잠금 범위·영향 요청을 기록합니다.
- incident 기록에 감지·판단·조치·복구 확인 시각을 따로 남겨 응답 구간을 설명할 수 있게 합니다.

## 9단계 — API 응답 지연 원인 분리 실험

별도 latency lab은 2026-11-22 UTC (2026-11-23 KST)에 실행했습니다. PostgreSQL 17.12의 `rewardlatencydb`와 API 8382를 사용했으며 API가 실제로 접속한 DB identity도 확인했습니다.

```text
Compose project=reward-latency
API published port=127.0.0.1:8382; DB port=127.0.0.1:55435
API datasource=jdbc:postgresql://db:5432/rewardlatencydb
API session current_database=rewardlatencydb current_user=reward_app
application_name=reward-latency-api
shared network=reward-latency_default
```

각 시나리오는 loopback에서 만든 합성 부하입니다. latency harness는 client `time.monotonic()` 요청 시간을 100개씩 모아 nearest-rank를 사용합니다. p95는 정렬된 100개 중 95번째 값, max는 100번째 값이며, Prometheus histogram quantile이나 운영 SLO가 아닙니다. `http.server.requests`는 Spring MVC Timer count/sum의 경로별 차이를 기록했습니다. API DB session 집계는 `pg_stat_activity`에서 `leader_pid IS NULL`인 client backend만 세고 parallel worker (`leader_pid IS NOT NULL`)는 별도로 남겼습니다. worker process 수를 Hikari 연결 수로 해석하지 않습니다.

수집 시점과 방식은 지표별로 구분했습니다. API client 응답 시간은 요청별로 측정했고, Spring Timer·Hikari·`pg_stat_activity`는 부하 요청이 진행되는 동안 sampler가 polling했습니다. 각 scan workload 전에 격리된 latency-lab PostgreSQL instance의 `pg_stat_statements` 통계를 reset하고, 100회 요청이 끝난 뒤 대상 DB/query의 누적 `calls`, `mean_exec_time`, buffers, rows를 읽었습니다. 이는 before/after snapshot 차분이 아닙니다. `EXPLAIN (ANALYZE, BUFFERS)`는 부하 묶음과 분리해 같은 predicate를 한 번 더 실행한 계획 표본입니다. 두 query-level 지표는 부하 중 동시 snapshot이 아니라 reset 후 workload 누적 통계와 별도 계획 실행입니다.

### 9-1. Hikari 연결 풀 고갈

Hikari 최대 연결 4, 획득 timeout 1,500ms, Tomcat thread 상한 128에서 100개 client가 동시에 2,000ms connection hold 요청을 보냈습니다.

| 측정 | 실제 결과 |
|---|---:|
| HTTP 결과 | 200 4건, 503 96건; 503 body reason `connection_pool_acquisition_timeout` 96건 |
| Client 응답 시간 | p50 1,632.449ms, p95 1,689.874ms, max 2,068.555ms |
| Spring HTTP timer | 100건, 평균 1,531.915ms |
| Hikari | active 최대 4, pending 최대 96, timeout 96, pool 최대 4 |
| API client DB sessions | active 최대 0, idle 최대 4, 전체 최대 4 |
| PostgreSQL Lock | Lock waiter 0, blocked session 0, wait event `Client/ClientRead` |

100개 요청은 Hikari에서 연결을 빌리기 전에 대기하거나 timeout됐습니다. 503 응답 body의 reason 수와 Hikari timeout counter 증가량이 모두 96으로 일치했습니다. DB 쪽 API 연결은 네 개 모두 `idle`이었고 PostgreSQL Lock은 관측되지 않았습니다. 따라서 이 시나리오의 503은 row Lock이나 SQL 실행 계획 때문이 아니라 pool acquisition timeout으로 분류했습니다.

### 9-2. PostgreSQL row Lock 대기

같은 단일 행을 4개 API 요청이 기다리는 라운드를 25회 반복해 100개 client 응답 표본을 모았습니다. 매 라운드 PostgreSQL `pg_stat_activity`에서 4개 active waiter와 Lock 대기 상태를 확인하고, recursive `pg_blocking_pids()` 경로로 각 waiter에서 synthetic blocker PID까지의 wait chain을 검사한 뒤 blocker `COMMIT` command tag와 psql exit 0을 확인했습니다.

| 측정 | 실제 결과 |
|---|---:|
| HTTP 결과 | 200 100건 |
| Client 응답 시간 | p50 183.788ms, p95 196.598ms, max 203.518ms |
| Spring HTTP timer | 100건, 평균 179.911ms |
| Hikari | active 최대 4, pending 0, timeout 0, pool 최대 4 |
| API client DB sessions | 최대 4 |
| PostgreSQL Lock | observer 표본 53개 중 24개에서 waiter; `Lock/transactionid`, `Lock/tuple` |
| Wait chain/조치 | 25 라운드, waiter chain 100개 검증, 매 라운드 blocker `COMMIT` 확인 |

PostgreSQL의 wait queue에서는 모든 waiter가 blocker에 직접 연결되지 않을 수 있습니다. 그래서 직접 edge 네 개를 요구하지 않고 `pg_blocking_pids()`를 재귀적으로 따라 각 API waiter가 같은 lab blocker에 도달하는지 검증했습니다. canonical run 첫 라운드 경로는 `176→184→279`, `184→279`, `185→184→279`, `186→184→279`였습니다. 이 HTTP client 시간에는 blocker 대기 외에도 request send와 관측·조치 시간이 포함되므로 순수 Lock 지속 시간으로 부르지 않습니다.

### 9-3. 100만 행 느린 SQL과 인덱스 적용

fixture는 1,000,000행 중 2,000행이 `marker LIKE '%needle%'`에 일치합니다. baseline과 튜닝 후 각각 100 API 요청을 concurrency 4로 실행했습니다. baseline 순서가 먼저이고 GIN 인덱스 적용 후 재측정이 뒤이므로 cache state를 통제한 반복 A/B 시험은 아닙니다. 두 결과 모두 `shared_blks_read=0`으로 기록됐습니다.

| 측정 | 인덱스 전 | GIN 적용 후 |
|---|---:|---:|
| API client 응답 p50 / p95 / max | 161.189 / 230.081 / 318.432ms | 10.892 / 18.687 / 21.910ms |
| Spring HTTP timer mean | 169.141ms | 7.456ms |
| `pg_stat_statements` mean execution | 165.681ms | 3.886ms |
| Query calls / returned aggregate rows | 100 / 100 | 100 / 100 |
| `EXPLAIN ANALYZE` execution | 37.289ms | 3.033ms |
| Plan | Parallel Seq Scan; leader 외 parallel worker process 최대 7, 7,353 shared hits | Bitmap Index Scan + Heap Scan, 2,017 shared hits |
| Hikari pool pending | 0 | 0 |

적용 SQL은 `GIN (marker public.gin_trgm_ops)`이고 인덱스 크기는 32,366,592 bytes (약 31 MiB)였습니다. 이 LIKE pattern에 pg_trgm operator class가 사용할 수 있다는 공식 PostgreSQL 문서와 실제 Bitmap Index Scan 계획을 확인했습니다. 튜닝 계획은 2,000 actual rows에 estimate 100 rows를 보여 20배 차이가 남았습니다. `ANALYZE` 뒤에도 추정 차이가 있어 선택도 통계를 더 조사할 수 있는 후속 질문으로 기록합니다. GIN 인덱스의 추가 쓰기 비용은 이번 latency 실험에서 측정하지 않았습니다. baseline에서 `pg_stat_activity`의 client backend는 최대 4였고, PostgreSQL parallel worker process는 별도 집계해 최대 7로 기록했습니다. worker process를 API connection 수로 세지 않았습니다.

### 9-4. 지표 해석과 원인 비교

| 원인 후보 | 부하 중 수집 | 요청 묶음 후 또는 별도 실행 |
|---|---|---|
| 연결 풀 대기 | HTTP status/client latency, `http.server.requests`, Hikari active/pending/timeout, API client sessions | 응답 body reason·Hikari timeout 모두 96; DB sessions 4 idle, Lock wait 0 |
| PostgreSQL row Lock | API latency/Timer, Hikari 지표, `pg_stat_activity` wait event 및 `pg_blocking_pids()` 경로 | waiter 4, `Lock/transactionid`/`tuple`, pool pending 0; 각 blocker COMMIT 확인 |
| 느린 SQL | API latency/Timer, Hikari, `pg_stat_activity` active query·parallel worker 표본 | reset 후 100회 실행 누적 `pg_stat_statements` 평균 165.681→3.886ms; 별도 EXPLAIN 37.289→3.033ms, buffers 7,353→2,017 |

Spring Boot는 MVC `http.server.requests` meter를 제공하고 Actuator Prometheus endpoint로 exposition 합니다. PostgreSQL은 `pg_stat_activity`로 현재 backend와 wait event, `pg_blocking_pids()`로 direct blocking 관계, `pg_stat_statements`로 normalized query별 실행 통계를 제공합니다. `EXPLAIN ANALYZE`에는 서버 실행 시간이 기록되고 API client 시간에는 HTTP 처리와 네트워크 전달이 포함되므로 두 구간을 나눠 측정했습니다.

## 10단계 — 사고 공유용 요약

**합성 incident:** 100개 동시 요청에서 API가 503을 반환했습니다. Hikari active는 pool 상한 4에 도달했고 pending/timeout은 각각 96이었습니다. HTTP body reason도 96건이 `connection_pool_acquisition_timeout`으로 일치했습니다. PostgreSQL API backend는 4개 idle, Lock wait는 0이었습니다. 따라서 관측 범위에서 직접 원인은 connection pool 획득 timeout입니다. 요청 burst 종료 뒤 pool은 4개 idle connection으로 돌아왔고 DB row 변경이나 Lock holder는 없었습니다.

**기술 지원 공유 초안:** “100개 동시 요청에서 96건이 HTTP 503으로 종료됐습니다. 응답 body reason과 Hikari timeout 증가량이 각각 96건으로 일치했고 pool pending도 최대 96이었습니다. 같은 시점 PostgreSQL API client session 네 개는 모두 idle이었고 Lock wait는 0이었습니다. 이번 재현의 지연 원인은 connection pool 획득 timeout으로 분류했습니다. 요청이 끝난 뒤 active/pending/timeout 증가 여부와 DB 세션을 다시 확인하겠습니다.”

이 절의 대표 수치는 [canonical latency 실행 JSON](../../../experiments/results/api_latency_diagnostics_2026-11-23.json) 한 건을 기준으로 동기화했습니다. 각 p95는 해당 JSON의 100개 client 표본 nearest-rank 순위 95입니다.

## 11단계 — 공식 개념과 참고 링크

- HikariCP의 [configuration reference](https://github.com/brettwooldridge/HikariCP#frequently-used): `connectionTimeout`은 pool에서 connection을 얻기 위해 기다리는 최대 시간입니다. 진단 endpoint는 이 획득 실패를 `SQLTransientConnectionException`으로 분류합니다.
- Spring Boot 3.5의 [Metrics](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html): MVC 요청 meter `http.server.requests`, Prometheus endpoint 설명.
- PostgreSQL 17의 [Monitoring Database Activity](https://www.postgresql.org/docs/17/monitoring-stats.html): `pg_stat_activity`, backend state, wait event.
- PostgreSQL 17의 [Session Information Functions](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-SESSION): `current_database()`, `current_user`, `pg_blocking_pids()` 설명. 문서는 soft blocking으로 인해 대기열 관계가 direct blocker만으로 끝나지 않을 수 있다고 정의합니다.
- PostgreSQL 17의 [`pg_stat_statements`](https://www.postgresql.org/docs/17/pgstatstatements.html): normalized SQL planning/execution statistics.
- PostgreSQL 17의 [`EXPLAIN`](https://www.postgresql.org/docs/17/using-explain.html): actual plan row/time/buffer 해석 및 EXPLAIN ANALYZE의 network caveat.
- PostgreSQL 17의 [`pg_trgm`](https://www.postgresql.org/docs/17/pgtrgm.html): GIN/GiST trigram operator class와 left-unanchored LIKE 지원.
