**기록 날짜:** 2026-11-22  
**상태:** 장애 보상, online schema 변경, migration 재시도, 보상 요청 동시성과 payload 충돌을 확인했습니다. 기존 API 바이너리 교차 실행과 검색 기간/cursor 경계도 검증했습니다.
**Phase 목적:** 이벤트 지급과 분리된 고객지원 장애 보상을 추가하고, 온라인 schema 변경 중 기존 CLAIM이 이어지는지, DDL Lock 대기와 migration 실패를 어떻게 관찰·복구하는지 직접 확인합니다.

## 0단계 — 시작 전 상태와 안전 경계

- P2 서비스는 Docker Engine ID 087938eb-2f8f-4d2f-bbde-9866fa90e37d의 dbapj 프로젝트였습니다. 기존 API 8082, DB 5432, 볼륨 dbapj_reward_pgdata를 확인했습니다.
- P3는 별도 Compose 프로젝트 reward-p3, DB rewardp3db, 볼륨 reward_p3_pgdata, API 8182, DB 포트 55432, UI 5175를 사용합니다. P2 DB에 migration, 보상 지급, reset 요청을 보내지 않았습니다.
- P3 DB는 PostgreSQL 17.12로 실행했습니다. 프로젝트가 요구하는 버전과 같으며 호스트에 설치된 PostgreSQL 14에 기대지 않았습니다.
- Docker socket은 기본 sandbox 권한에서 접근이 거부되어, 승인된 P3 격리 작업으로 Docker Engine과 기존 컨테이너/볼륨을 먼저 읽기 전용 확인한 다음 P3 프로젝트만 조작했습니다.
- 실습 트리거는 현재 database가 rewardp3db인지 확인하고, 지정한 event_id의 reward_grants INSERT만 실패시킵니다. 스키마·프로시저의 다른 기능이나 P2 DB에는 적용하지 않습니다.

## 3단계 — 빌드와 실험 기반 준비

### 실행 결과

- frontend 디렉터리에서 npm run build가 성공했습니다.
- 로컬 Maven 패키징은 사용자 홈의 .m2 cache에 쓸 수 없어 실패했습니다. 같은 소스는 Docker multi-stage build에서 Maven BUILD SUCCESS로 패키징했습니다. 테스트는 실행하지 않았습니다.
- Docker compose 설정 검증과 p3_lock_demo.py의 Python 구문 분석이 통과했습니다.
- P2 API/DB/볼륨을 먼저 확인한 뒤 새 프로젝트 이름으로 P3를 시작했습니다. P3만 조작하는 compose 명령에 -v를 붙이지 않았습니다.

격리 프로젝트를 시작하는 실행 형태는 다음과 같습니다. migration 단계별 확인은 P3_FLYWAY_TARGET 값만 6, 7, 8, 9, 11로 바꿔 API를 다시 만들어 순차 적용했습니다.

~~~sh
export DOCKER_HOST=unix:///private/tmp/reward-colima/active-docker.sock
P3_FLYWAY_TARGET=16 APP_P3_COMPENSATION_ENABLED=true APP_DEMO_WALLET_RESET_ENABLED=true \
  docker compose -p reward-p3 -f compose.p3.yaml up --build -d
~~~

### 준비 중 발생한 문제와 처리

1. 첫 P3 DB 초기화 때 bootstrap script가 rewarddb 이름을 고정 사용해 rewardp3db 연결에 실패했습니다. 역할 생성 스크립트를 POSTGRES_DB 변수 사용으로 고쳤습니다.
2. 실패한 초기화는 새로 만든 P3 빈/부분 volume에만 해당했습니다. P3 프로젝트만 내리고 P3 volume만 제거한 뒤 다시 초기화했습니다. P2 volume은 삭제하거나 재생성하지 않았습니다.
3. Flyway target을 99로 넘긴 첫 API 기동은 존재하지 않는 migration target 때문에 실패했습니다. Flyway history는 V9에 그대로였고 DB schema 변경은 적용되지 않았습니다. compose 기본값과 안내 명령을 실제 마지막 버전인 11로 고친 뒤 재기동했습니다.

| V6 기존 지급 | user 101이 event 1 CLAIM | HTTP 200, PAID, grant 1. 이후 ledger는 EVENT 2행, wallet 1000/200. |

| V8 제약 확장 | P3 DB에 V8 NOT VALID 제약 적용 | 두 제약 convalidated=false. 과거 잘못된 source 행은 남아 있었고 새 user 103 CLAIM은 PAID, grant 3. |
| V9 첫 검증 | 잘못된 source_type=LEGACY_INVALID 행을 둔 채 target 9 적용 | `wallet_ledger_source_consistency_ck` 검증 실패를 확인했습니다. Flyway 이력은 V8을 유지했고 두 제약은 NOT VALID 상태였습니다. 원인 행을 forward fix한 뒤 V9 검증을 완료했습니다. |
| Forward Fix | P3의 문제 행 id 1만 source_type=EVENT로 수정하고 V9 재시도 | V9 성공. 두 제약 모두 convalidated=true. 기존 wallet/grant 지급액은 바꾸지 않았습니다. |
| V10/V11 적용 | target 11로 API 기동 | V10 보상 프로시저와 V11 reset 호환 migration이 적용되어 Flyway v11, API health UP. |
| V11 이후 기존 CLAIM | 별도 event 4, user 103, Money 300/Point 30 | HTTP 200 PAID, grant 5. 기존 EVENT 경로가 새 출처 제약 아래서도 지급됐습니다. 이벤트는 확인 후 CLOSED. |

각 단계는 다음과 같이 API만 재생성해 적용했습니다. P2 프로젝트 이름이나 P2 compose 파일은 사용하지 않았습니다.

~~~sh
P3_FLYWAY_TARGET=7 APP_P3_COMPENSATION_ENABLED=false \
  docker compose -p reward-p3 -f compose.p3.yaml up --no-deps -d --force-recreate api
~~~

target 값은 위 순서대로 바꿨습니다. target 99를 잘못 전달했을 때는 Flyway가 없는 migration 번호라고 거부했고 V9에서 DB가 유지됐습니다. compose 기본값과 안내 명령을 11로 고친 뒤 V10/V11 적용을 완료했습니다.

### Backfill 판단

이 데이터에서는 과거 모든 wallet_ledger 행이 이벤트 지급이고 행별 계산 규칙이 필요하지 않았습니다. PostgreSQL 17.12 catalog가 V7 상수 기본값을 기존 행에 EVENT로 표시하는 것을 확인해 별도 UPDATE backfill을 생략했습니다.

## 5단계 — migration 실패와 안전한 재시도

이번 실패는 일부 schema 단계가 적용된 뒤 검증 migration만 실패하는 상황을 재현했습니다.

1. V8에서 source 일관성 CHECK와 보상 FK를 NOT VALID로 추가했습니다. 새 쓰기는 제약을 받지만 과거 행 검증은 V9까지 미뤄졌습니다.
2. P3 DB에 source_type=LEGACY_INVALID인 과거 ledger 행을 남겨 놓고 V9를 실행했습니다.
3. CHECK 검증이 실패했고 Flyway max version은 8로 유지됐습니다. DB catalog에서 두 제약도 convalidated=false였습니다.
4. 원인 행을 EVENT로 바로잡고 V9를 다시 실행했습니다. Flyway v9와 convalidated=true를 확인했습니다.

실패한 migration을 삭제하거나 새 형식 테이블을 DROP하지 않았습니다. 이미 V8이 성공해 존재하는 단계는 유지하고 잘못된 데이터만 바로잡은 뒤 실패 migration을 다시 적용했습니다.

## 6단계 — DDL Lock 대기와 후속 SELECT

experiments/p3_lock_demo.py가 별도 PostgreSQL 연결 A/B/C를 만들고 snapshot을 저장했습니다.

~~~sh
export DOCKER_HOST=unix:///private/tmp/reward-colima/active-docker.sock
python3 experiments/p3_lock_demo.py
~~~

| 세션 | 작업 | 관측 결과 |
|---|---|---|
| A | wallet_ledger SELECT 후 트랜잭션을 열고 25초 대기 | pid 1420, Timeout/PgSleep, AccessShareLock 보유 |
| B | lock_timeout 8초 후 ALTER TABLE로 probe column 추가 | pid 1441, A를 blocker로 둔 AccessExclusiveLock 대기. 8.10초 후 lock timeout으로 실패 |
| C | B가 요청한 뒤 wallet_ledger SELECT | pid 1455, B 뒤에서 AccessShareLock 대기. B timeout 후 A가 끝나기 전에 재개되어 결과 6 반환 |
| B 재시도 | A commit 뒤 같은 ALTER 수행 | 성공, 0.140초. lock probe column 제거는 0.092초 |

핵심 관측은 ALTER가 기존 SELECT 트랜잭션의 AccessShareLock을 기다리고, 대기 중인 AccessExclusiveLock 뒤에 온 SELECT도 lock queue에 걸렸다는 것입니다. 처음 수동 실행은 blocker snapshot을 놓쳤습니다. 그래서 pg_stat_activity 상태를 확인한 뒤 다음 세션을 시작하도록 스크립트를 만들고 같은 상황을 다시 관측했습니다.

## 12단계 — V12~V14 앱 권한과 CS 보상 재시도·동시성 재검증

P2에서 확인한 권한 경계는 별도 볼륨의 P3/P4 DB에도 각각 migration해야 합니다. `compose.p3.yaml`의 Flyway target을 14로 올리고 P3 API를 rebuild했습니다. Flyway는 V11에서 V12, V13, V14를 적용했습니다. P3 API는 8182, DB는 55432이며 기존 rewarddb와 볼륨을 공유하지 않습니다.

실행 명령:

~~~sh
export DOCKER_HOST=unix:///private/tmp/reward-colima/active-docker.sock
docker compose -p reward-p3 -f compose.p3.yaml up -d --build api
python3 experiments/p3_compensation_acceptance.py
~~~

스크립트는 새 사용자·지갑을 만들고 `reward_app` 권한으로 HTTP compensation API를 호출합니다. `X-Demo-Role`은 로컬 운영자 기능 경로를 선택합니다.

### 단일 요청과 같은 장애 건 재시도

| 요청 | 응답 | DB 대사 |
|---|---|---|
| 새 요청 UUID | `PAID`, compensationId 48 | compensation 1건, ledger 2행 |
| 같은 UUID·같은 payload 재시도 | `REPLAYED`, compensationId 48 | 추가 compensation/ledger 없음 |
| 새 UUID·같은 event/incident/user | `ALREADY_COMPENSATED`, compensationId 48 | wallet 2500/500, ledger 합계 2500/500 |
| 새 UUID·같은 업무 키, reason/operator/Money/Point 중 하나 변경 | HTTP 409 | 위 네 경우 모두 추가 compensation/ledger 또는 wallet 변경 없음 |

### 다른 UUID로 같은 장애 건에 동시에 보상

- 세션 A는 `SET ROLE reward_app` 상태에서 보상 procedure를 실행하고 커밋을 보류했습니다.
- API 세션 B는 다른 request UUID로 같은 `(event_id, incident_reference, user_id)`를 요청했습니다.
- `pg_stat_activity`에서 B가 `wait_event_type=Lock`, `wait_event=transactionid`로 A PID를 기다리는 것을 확인하고 A를 COMMIT했습니다.
- A는 `PAID`, B는 HTTP 200 `ALREADY_COMPENSATED`였습니다. 보상 1건, ledger 2행, wallet/ledger 합계는 Money 3300 / Point 700으로 일치했습니다.

### 같은 UUID를 다른 사용자·사유로 동시에 재사용

- 세션 A가 사용자 A에 UUID X를 사용해 보상을 만들고 transaction을 보류했습니다. API 세션 B는 UUID X를 사용자 B·다른 incident·다른 금액으로 사용했습니다.
- PostgreSQL에서 B가 A PID에 의해 `wait_event=advisory` 상태인 것을 관측한 뒤 A를 COMMIT했습니다.
- B는 HTTP 409를 받았습니다. SQL 결과는 UUID 소유 보상 1건, 사용자 A 보상/ledger 1건/2행, 사용자 B 보상/ledger 0건/0행, 지갑 A 4400/300, 지갑 B 0/0이었습니다.

### CLAIM과 compensation 사이 request UUID 재사용

V1/V7의 `UNIQUE(request_id)`는 각각의 지급 테이블 안에서 중복을 차단합니다. P2/P3 API 계약은 두 출처가 같은 UUID 공간을 사용하므로 공통 V16에서 상대 테이블도 확인하게 했습니다. P4가 이미 사용하는 V15를 보존하기 위해 공통 변경은 V16에 배치했습니다.

기존 `rewardp3db`는 공통 V15를 적용한 뒤 파일 버전이 V16으로 이동했습니다. [guarded history alignment](../../../experiments/sql/renumber_local_p3_global_request_migration.sql)는 현재 DB명, migration description/checksum, 기존 V16 부재를 확인한 후 history의 version만 15에서 16으로 바꾸었습니다. API 재기동 시 Flyway validation은 새 경로와 기존 checksum을 확인했습니다.

2026-11-23 acceptance는 양방향 재사용을 호출하고 사후 잔액과 원장을 비교했습니다.

| 최초 지급 | 재사용 요청 | 최초 결과 | 재사용 결과 | 사후 지급 테이블·원장·지갑 |
|---|---|---|---|---|
| CLAIM | compensation | HTTP 200 `PAID` | HTTP 409 | grants 1, compensations 0, ledger 2, wallet/ledger 1000/200 |
| compensation | CLAIM | HTTP 200 `PAID` | HTTP 409 | grants 0, compensations 1, ledger 2, wallet/ledger 1800/350 |

두 사용자 reset은 각각 최초 지급 1건과 ledger 2행을 제거했습니다. 전체 응답과 각 행 대사는 [P3 compensation acceptance JSON](../../../experiments/results/p3_compensation_acceptance_2026-11-23.json)에 기록했습니다.

### 교차 지급 종류 동시 경합

순차 재사용 외에 두 지급 종류가 같은 UUID로 동시에 진입하는 경우도 확인했습니다. 첫 프로시저를 `reward_app` 호출자로 실행한 뒤 transaction을 보류하고, 반대 종류 API 요청을 보내 `pg_stat_activity.wait_event=advisory`와 `pg_blocking_pids()`의 blocker PID를 관측한 다음 첫 트랜잭션을 COMMIT했습니다.

| 먼저 열린 지급 | 대기 API | waiter ← blocker PID | 대기 해제 후 응답 | 지급 행 / 원장 / 지갑·원장 합계 |
|---|---|---|---|---|
| CLAIM | compensation | 72241 ← 73958 | HTTP 409 | grants 1, compensations 0, ledger 2, Money/Point 1000/200 |
| compensation | CLAIM | 72241 ← 74013 | HTTP 409 | grants 0, compensations 1, ledger 2, Money/Point 1800/350 |

두 경로 모두 첫 요청만 `PAID`가 되고 반대 요청은 같은 transaction advisory lock을 기다린 뒤 `REQUEST_ID_CONFLICT`가 됐습니다. 각 테스트 사용자는 검증 뒤 지급 1건과 ledger 2행을 reset했습니다.

### 쓰기 권한과 search_path 확인

- `reward_app`의 실제 wallets UPDATE, compensations INSERT, wallet_ledger DELETE, reward_grants DELETE는 거부됐습니다. 지급 API 호출과 reset API 호출은 명시된 EXECUTE 경로로 성공했습니다.
- reward schema의 `SECURITY DEFINER` routine 7개는 모두 `search_path=pg_catalog, reward, pg_temp`; PUBLIC EXECUTE routine 0개였습니다. `reward_app` 실행 목록은 `grant_compensation`, `grant_event_reward`, `reset_local_user_wallet`, `reset_all_local_wallets`였고 내부 reset helper는 실행할 수 없었습니다.
- owner는 `reward_migration`입니다. 이 LOGIN role은 reward schema와 11개 테이블의 owner이며 superuser/CREATEROLE/CREATEDB/REPLICATION/BYPASSRLS가 아니고 role membership도 0개입니다. SECURITY DEFINER는 이 object-owner 권한으로 실행하며 `reward_app`에는 직접 지급 DML 권한을 주지 않습니다.
- `pg_has_role(reward_app,reward_migration,MEMBER/USAGE/SET)`은 모두 false였고, 실제 reward_app DB 로그인에서 `SET ROLE reward_migration`은 `permission denied to set role`로 거부됐습니다.
- 업무 UNIQUE 키는 중복 행을 차단하고, V13 procedure는 winner snapshot을 비교해 바뀐 reason/operator/Money/Point 요청을 HTTP 409로 분류합니다. 같은 내용의 다른 request UUID만 `ALREADY_COMPENSATED`로 반환합니다.

### Disposable user 단건 reset

모든 보상·동시성 검증이 끝난 뒤 acceptance가 만든 사용자 한 명에게 `POST /api/me/wallet/reset`을 보냈습니다. 응답은 `usersReset=1`, `compensationsDeleted=1`, `ledgerRowsDeleted=2`였고, 이후 SQL은 사용자 1명 유지, wallet 0/0, compensation 0건, ledger 0건을 반환했습니다. P3의 나머지 사용자와 지급 evidence는 reset하지 않았습니다.

### DB 기본 격리 수준이 다른 환경에서 compensation transaction 관측

P3 API의 compensation INSERT도 같은 snapshot 경계가 있으므로 `rewardp3db` 기본값을 `REPEATABLE READ`로 잠시 바꾸고 API를 새로 띄웠습니다. 임시 AFTER INSERT trigger에서 기록한 두 행 모두 `read committed | reward_app | reward_migration`이었습니다. 같은 요청 재시도, 변경 payload 네 종류의 HTTP 409, 서로 다른 UUID의 업무키 경합과 같은 UUID 재사용 경합이 기대 결과를 냈습니다. observer 객체를 제거하고 DB 기본값을 `READ COMMITTED`로 복구한 뒤 API를 재시작했습니다.

### 운영 화면 전체 초기화의 별도 DB acceptance

`reward-reset-validation` 전용 프로젝트의 새 `rewardresetdb`에서 CLAIM 1건, 장애 보상 1건, BATCH 3건을 만들어 grant 4건, compensation 1건, ledger 10행, 비영 지갑 3개, batch run 1건을 구성했습니다. acceptance는 destructive POST 직전 API datasource가 `rewardresetdb`, published port가 `127.0.0.1:8383`, Compose project가 `reward-reset-validation`인지 확인한 뒤 `POST /api/admin/wallets/reset-all`을 호출합니다. API 주소를 환경변수로 다른 phase에 돌릴 수 없도록 고정했습니다.

HTTP 200 응답은 `usersReset=3`, `grantsDeleted=4`, `compensationsDeleted=1`, `ledgerRowsDeleted=10`이었습니다. 임시 row trigger 18개 기록은 동일 transaction ID 하나와 `read committed | reward_app | reward_migration`을 표시했습니다. 기록된 DML은 ledger DELETE 10, compensation DELETE 1, grant DELETE 4, wallet UPDATE 3입니다. 사후 DB에서는 users 3, events 3, recipients 6, batch_runs 1, wallets 3이 보존됐고 grants/compensations/ledger는 0, 비영 지갑 및 총 잔액도 0이었습니다. 이 reset 검증은 기존 P2/P3/P4 volume에 요청하지 않았습니다.
- PostgreSQL transaction advisory lock은 동일 키 호출을 transaction 종료까지 직렬화합니다. 다른 키의 업무 UNIQUE 충돌은 별도 `transactionid` 대기로 관측했습니다.
- 해당 실습은 보상 procedure의 원자적 실행과 로컬 데모 권한 경로를 실제 API·DB 상태로 확인합니다.
