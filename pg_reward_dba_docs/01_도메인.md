# 01. 도메인 문서

## 1. 서비스 개요

기간 한정 이벤트를 운영하고, 이벤트 규칙에 따라 게임머니와 포인트를 사용자 지갑에 지급합니다. 이벤트 지급과 장애 보상은 출처가 구분된 원장으로 기록하며, 지급 검색·정합성 확인·운영 진단을 같은 흐름에서 실습합니다.

## 2. 행위자와 작업

| 행위자 | 주요 작업 |
|---|---|
| 사용자 | 이벤트 확인·수령, 지갑 잔액과 최근 지급 조회 |
| 이벤트 운영자 | 이벤트 생성, OPEN/CLOSED 전환, 예약 대상과 지급액 관리 |
| 고객지원 담당자 | 사용자·기간·출처별 지급 검색, 장애 보상 요청 |
| DBA | migration 배포, 세션·Lock·쿼리 계획 관측, 정합성 대사, 복구 절차 수행 |

## 3. 재화와 지급 기록

- `MONEY`: 지갑에 저장하는 게임머니 단위.
- `POINT`: 이벤트 포인트 단위.
- `wallets.money_balance`, `wallets.point_balance`: 사용자별 현재 잔액 요약.
- `wallet_ledger`: 지급 출처·재화·금액·사용자·시각을 기록하는 변동 원장.
- `reward_grants`: 이벤트 지급 사실과 당시 지급액을 보존합니다.
- `compensations`: 장애 보상의 사유·대상·요청 정보와 지급액을 보존합니다.

## 4. 지급 유형

### 4.1 `CLAIM` — 사용자 직접 수령

1. 사용자가 `POST /api/events/{id}/claims`와 `Idempotency-Key`를 보냅니다.
2. API가 사용자·요청 문맥을 만들고 `grant_event_reward`를 호출합니다.
3. procedure가 이벤트 정책과 지급 가능 시각을 확인합니다.
4. `reward_grants`, `wallets`, `wallet_ledger`를 호출 트랜잭션 안에서 갱신합니다.
5. 새 지급은 `PAID`, 동일 키 재요청은 `REPLAYED`, 다른 키의 기존 지급은 `ALREADY_GRANTED`로 전달됩니다.

### 4.2 `BATCH` — 예약 대상 일괄 지급

1. 운영자가 이벤트를 등록하고 `(event_id,user_id)` 단위로 `event_recipients`를 확정합니다.
2. 작업자가 `scheduled_at` 이후 지급을 시작합니다.
3. 작업자는 사용자별로 공용 지급 procedure를 호출하고 트랜잭션을 커밋합니다.
4. 재개 시 `event_recipients LEFT JOIN reward_grants`로 미지급 사용자를 계산합니다.
5. `batch_runs`에는 실행 상태와 시간·오류를 기록합니다.

### 4.3 `COMPENSATION` — 장애 보상

1. 운영자가 장애 참조 ID, 사용자, 사유, 지급액과 요청 ID를 등록합니다.
2. `/api/admin/compensations`가 권한과 payload 일치를 확인한 뒤 보상 procedure를 호출합니다.
3. `compensations`, 지갑, `wallet_ledger`를 한 트랜잭션에서 갱신합니다.
4. `(event_id, incident_reference, user_id)` 업무 키가 같은 재요청은 기존 요청 내용과 지급 결과를 기준으로 응답합니다.
5. 통합 지급 검색은 사용자·기간·출처와 커서를 조건으로 조회합니다.

## 5. 업무 규칙

| ID | 규칙 |
|---|---|
| BR-01 | 이벤트 상태 전이는 `DRAFT → OPEN → CLOSED` 순서입니다. |
| BR-02 | CLAIM은 OPEN 상태와 `[starts_at, ends_at)` 구간을 따릅니다. |
| BR-03 | BATCH는 확정된 `event_recipients`만 지급하며 `scheduled_at` 이후 실행합니다. |
| BR-04 | 이벤트 방식은 `CLAIM` 또는 `BATCH` 중 하나입니다. |
| BR-05 | 동일 이벤트·사용자 조합의 지급은 UNIQUE 제약으로 한 건을 유지합니다. |
| BR-06 | 재화별 지급액은 0 이상이고 두 지급액 중 하나는 0보다 큽니다. 지갑 잔액은 0 이상입니다. |
| BR-07 | `reward_grants`와 `compensations`는 지급 시점의 재화별 금액을 보존합니다. |
| BR-08 | 지급 사실, 지갑 갱신, 원장 삽입은 한 트랜잭션으로 처리합니다. |
| BR-09 | 동일 업무 요청 재시도에는 같은 request ID를 사용합니다. |
| BR-10 | 요청 타임아웃 뒤에는 DB의 지급 행을 조회해 결과를 판정합니다. |
| BR-11 | BATCH 재개 대상은 실제 대상 명단과 커밋된 지급 행의 차집합으로 계산합니다. |
| BR-12 | 지급 원장은 변경 이력으로 유지하고, 데이터 정정은 별도 보상·정정 업무로 기록합니다. |

## 6. 운영 시나리오

1. 사용자가 CLAIM 이벤트를 수령하고 지갑·원장 변화를 확인합니다.
2. 1,000명 BATCH 작업 중 PostgreSQL 프로세스를 중지하고 Crash Recovery 뒤 남은 대상을 재처리합니다.
3. 장애 참조 ID를 사용해 COMPENSATION을 지급하고 이벤트 지급과 함께 검색합니다.
4. 1,000,000건 원장 fixture의 조회 계획과 인덱스·WAL 비용을 비교합니다.
5. 연결 풀 대기, DB Lock 대기, 느린 SQL을 API·Hikari·PostgreSQL 관측값으로 분리합니다.
6. PITR 및 HA 실습은 후속 운영 시나리오로 이어갑니다.

## 7. 구현 화면과 진단 경로

- 사용자 화면: 이벤트 목록·상세, CLAIM, 지갑, 지급 이력.
- 운영 화면: 이벤트 상태·예약 대상·지급 실행과 내 지갑/전체 사용자 초기화.
- 운영 검색: 장애 보상 등록, 출처별 지급 이력 조회.
- DBA 진단: SQL, PostgreSQL session/wait statistics, EXPLAIN, Flyway와 실습 기록.
