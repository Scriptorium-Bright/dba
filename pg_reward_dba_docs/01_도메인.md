# 01. 도메인 문서

## 1. 한 문장 설명

온라인 게임에서 기간 한정 이벤트를 운영하고, 정해진 규칙에 따라 게임머니와 이벤트 포인트를 사용자 지갑에 지급한다. 고객지원팀은 장애 발생 시 별도 보상을 지급할 수 있다(후속 Phase).

서비스는 **DB 운영 실험의 업무 배경**이다. 전투/아이템/결제/로그인 시스템은 만들지 않는다.

## 2. 행위자와 화면

| 행위자 | 화면 | 실제 행동 |
|---|---|---|
| 사용자 | 이벤트 목록·상세, 내 지갑·지급 이력 | 수령형 이벤트 확인, 수령 버튼, 잔액 및 최근 지급 조회 |
| 이벤트 운영자 | 이벤트 관리 | 생성, OPEN/CLOSED 전환, 지급 재화 및 지급 방식 결정, 일괄 대상 선정·실행 예약 |
| 고객지원 담당자(확장) | 지급 검색·보상 | 사용자·기간·출처별 지급 조회, 장애 보상 요청 |
| DBA | 별도 운영 화면/CLI/Grafana | SQL, 세션, Lock, 실행 계획, 복제, 복구 상태 확인 및 관리 |

## 3. 재화

- `MONEY`: 게임머니(예: Gold). **현금 또는 결제 수단 아님**.
- `POINT`: 이벤트 포인트. 별도 단위를 가진 게임 재화.
- `wallets.money_balance`, `wallets.point_balance`: 조회용 현재 잔액.
- `wallet_ledger`: 지급 시점의 불변 지급 근거. 지급 때마다 Money/Point별 0~1행씩 기록하며, 0인 종류는 원장 행을 만들지 않는다.
- 실험 범위에서는 **지급만 허용**하며 차감, 환불, 유효기간 소멸 등은 제외한다.

## 4. 이벤트 종류

### 4.1 `CLAIM` — 사용자 직접 수령

예: 겨울 출석 이벤트(12월 1~31일, 게임머니 1,000 + 포인트 200). 운영자가 이벤트를 OPEN하면 사용자가 버튼으로 요청한다.

1. 사용자가 `POST /api/events/{id}/claims` 호출.
2. API가 사용자 식별자와 요청 ID를 추출한다.
3. 초기 P1 구현은 API 서비스가 이벤트 OPEN/기간과 기존 지급을 검증하고 트랜잭션으로 처리한다. P2에서 같은 계약을 지급 SP로 옮긴다.
4. `reward_grants` 1행, `wallets` 잔액 갱신, `wallet_ledger` 최대 2행을 **단일 트랜잭션**에서 처리한다.
5. 실제 COMMIT 성공 후 신규 지급 응답을 반환한다.

### 4.2 `BATCH` — 예약된 대상에게 일괄 지급

예: 서버 점검 기념 보상(오전 09:00, 대상 1,000명, 게임머니 500 + 포인트 100).

1. 운영자가 이벤트를 등록하고 대상자를 `event_recipients`에 확정한다.
2. 서버 스케줄러/작업자가 이벤트 기간 내로 설정한 예약 시각에 실행을 시작한다.
3. 미지급 대상자를 조회하고 **사용자별 SP는 재사용**한다.
4. 배치 크기 `B`명씩 묶거나 사용자별로 트랜잭션을 커밋하는 방식을 비교한다. P2에서는 가장 단순한 사용자별 커밋부터 구현한다.
5. 장애 후 재실행 시 `event_recipients`와 `reward_grants`를 대조한다.

**비즈니스 정책:** `BATCH`의 자동 지급 허용은 예약 실행 조건을 따른다. 스케줄이 지연되어 이벤트 종료 시각을 넘어가도, `CLOSED`로 수동 중단하지 않았다면 사전 확정된 대상 지급을 재개할 수 있다. 현재 정책은 가정이며 실험 전 고정한다.

### 4.3 `COMPENSATION` — 고객지원 장애 보상(후속)

고객지원 담당자가 장애 보상 사유·대상·담당자·지급액을 등록한다. 이벤트 수령과 다른 출처이므로 P3에서 `compensations` 테이블과 원장 출처 제약을 추가한다. 기존 이벤트 지급 데이터와 함께 검색한다.

## 5. 업무 규칙

| ID | 규칙 |
|---|---|
| BR-01 | 이벤트는 `DRAFT → OPEN → CLOSED`; v1에서 CLOSED 재오픈 없음. |
| BR-02 | `CLAIM`은 OPEN이고 서버 기준 `[starts_at, ends_at)` 구간에서만 가능. |
| BR-03 | `BATCH`는 OPEN인 이벤트에 대해 사전 등록된 `event_recipients`만 지급. 실행 시간은 `scheduled_at` 이후. |
| BR-04 | 이벤트에는 `CLAIM` 또는 `BATCH` 방식 하나만 부여. v1에서 중간 변경 불허. |
| BR-05 | 같은 이벤트의 동일 사용자에게 정상 지급은 최대 1회. |
| BR-06 | 지급 금액은 재화별 0 이상, 둘 중 하나는 0 초과. 잔액은 음수 불가. |
| BR-07 | 실제 지급 금액을 `reward_grants`에 스냅샷 저장. 이벤트 보상 정책 변경 후에도 과거 지급액 불변. |
| BR-08 | 지급 이력 + 지갑 변경 + 원장 기록은 같은 DB 트랜잭션. |
| BR-09 | 요청 ID는 재시도 동안 동일하게 사용. 중복 수령의 재화 증가는 0. |
| BR-10 | 클라이언트의 타임아웃은 지급 여부 `UNKNOWN`이다. 복구 후 DB를 조회해 판정. |
| BR-11 | `BATCH` 작업자는 DB 커밋 결과를 기준으로 남은 대상을 결정한다. 워커의 메모리 카운터는 참조 정보. |
| BR-12 | 지급 원장은 보정 가능한 업무가 추가되기 전까지 수정·삭제하지 않는다. 장애 삭제는 별도 실험 환경에서만 재현. |

## 6. 가상 업무 흐름

1. **이벤트 A (CLAIM)** — 101번 사용자가 버튼 클릭 → Money +1,000 / Point +200, 지갑·원장 반영.
2. **이벤트 B (BATCH)** — 1,000명 대상 자동 지급 → 600명의 트랜잭션이 커밋된 후 PostgreSQL 프로세스 장애 → Crash Recovery → 400명 재처리(가정).
3. **장애 보상 기능 요청** — 고객지원팀이 영향 사용자에게 별도 보상 지급 → 테이블·SP를 운영 중 변경.
4. **지급 내역 누적** — 조회 SQL이 느리다는 신고 → DBMS의 실제 실행 계획과 통계로 원인 분석.
5. **HA/DR 확장** — 단일 DB 장애 재현 후 Primary–Standby, Failover, PITR 실험.

## 7. UI 우선 범위

- P1: 사용자 이벤트/지갑, 운영자 이벤트 등록·오픈·종료.
- P2: 배치 대상 명단·실행 시작/진행 상태(간단한 운영 화면), 지급 완료/미완료 건수. 실제 장애 주입은 CLI.
- P3: 고객지원 지급 검색·보상.
- P4+: DB 내부 지표는 우선 Grafana/CLI 사용. 커스텀 DBA UI 개발은 추후 선택.

## 8. 범위 제외

실제 게임 접속·결제·실제 화폐·구매/차감·계정 인증 제품화·정교한 권한 화면·메시지 브로커·여러 서비스 분할. 테스트 사용자 선택과 관리자 역할은 개발용 제한 구현으로 시작한다.
