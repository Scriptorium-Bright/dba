# 03. 프로젝트 설계서

## 1. 문제 정의

일반적인 게임 이벤트 보상 지급 서비스에서 DB 운영자는 테이블·SP의 변경을 안전하게 배포하고, 지급 데이터의 일관성을 확인하고, SQL 성능 저하와 DB 장애를 처리해야 한다. 본 프로젝트는 지속적인 보상 트래픽과 운영 변경 상황을 **실험용 DB 환경에서 재현**해, 조사·조치·검증까지 수행한다.

## 2. 프로젝트의 핵심 산출물

1. 실제 요청이 발생하는 소형 이벤트 서비스(React + Spring Boot).
2. PostgreSQL 테이블·제약·Stored Procedure + Git/Flyway 이력.
3. 장애·Lock·SQL 성능·복제·복구 실험 환경.
4. DBA 런북과 재현 가능한 자동 검증 및 비교 결과.

**서비스의 성공 지표:** 보상 지급/조회가 정확하게 동작.

**DBA 프로젝트의 성공 지표:** 문제가 나타난 때 무엇을 관측했는지, 왜 조치했는지, 동일 조건 재실험 결과와 운영 비용을 입증.

## 3. 책임 경계

| 관심사 | API/작업자 | PostgreSQL / DBA |
|---|---|---|
| HTTP/화면 | 요청 식별·권한·응답 | 직접 담당하지 않음 |
| 이벤트 운영 정책 | 요청 생성·유효성 제어 | 이벤트 상태·규칙 보존 및 지급 시 검증 |
| 지급 처리 | 단일 SP 호출과 트랜잭션 경계 | `UNIQUE`, `RETURNING INTO`, 지갑/원장 원자적 갱신 |
| 중복 재시도 | 같은 request_id 유지·상태 재조회 | 재호출 시 기존 커밋 결과 확인, 추가 지급 차단 |
| 예약 일괄 지급 | 대상 배치 호출·재시작·오류 기록 | 지급 상태·실제 커밋 기록이 진실의 원천 |
| 성능 | 호출 패턴·API p95·타임아웃 | 실행 계획·쿼리 시간·I/O·Lock 원인 진단 |
| 변경 배포 | 구/신 버전 호환·앱 릴리스 | DDL/SP 적용 순서·잠금·배포 검수·복구 |
| 장애 복구 | 재연결·미지급 재시도 | Crash Recovery/WAL, HA 전환, PITR 및 검증 |

## 4. 데이터 정합성 원칙

- **이벤트 지급 1회:** `UNIQUE(event_id,user_id)`.
- **요청 중복:** `request_id` 유일 + 사용자/이벤트 재확인. 다른 이벤트에 같은 요청 ID를 재사용하면 오류 처리.
- **재화 둘 다 처리:** `wallets` 한 행에서 두 잔액을 원자적으로 업데이트.
- **원장:** 한 지급에 대해 Money/Point 각각 금액이 0보다 큰 경우만 1행; `UNIQUE(reward_grant_id,currency_type)`.
- **결과 상태:** 워커에서 요청이 성공했다고 적은 숫자와 커밋된 DB 행 수는 다를 수 있으므로 반드시 대조.
- **동시성:** 기본 격리 수준 `READ COMMITTED`, `INSERT ... ON CONFLICT DO NOTHING RETURNING id INTO ...`와 후속 SELECT로 승자 지급 확인; 이벤트 정책 변경과 지급 중 정책 경합은 이벤트 행 `FOR SHARE` 등으로 조정.

## 5. 기술 선택 (초안)

| 레이어 | 선택 | 근거 |
|---|---|---|
| Frontend | React + Vite | 장애 영향과 원장 변화를 직접 확인 |
| Backend | Java 21 + Spring Boot | 익숙한 서버, HTTP·DB 연결만 구현 |
| DB | PostgreSQL 17 | 정식 SP, WAL, 복제, Lock·실행 계획 실습 |
| Migration | Flyway | 테이블·SP 버전 관리 |
| Workload / CLI | Python + SQL | 반복 지급·장애·정합성 실험 |
| Local Infra | Docker Compose | 일관된 DB·API 환경 |
| Monitoring | SQL+로그 우선, 이후 Prometheus/Grafana | 원인 확인에 필요한 지표부터 |
| HA | Patroni + etcd + Proxy(확장안) | 승격·리더 관리·연결 전환 실습 |
| Backup | Base Backup + WAL Archive | 별도 인스턴스 복원/PITR 검증 |
| Cloud Native | CloudNativePG(선택 P8) | 별도 PostgreSQL 운영 환경 비교 |

## 6. 개발·운영 흐름

1. P0에서 `v1` 데이터 모델과 역할별 DB 접속 설정.
2. P1에서 사용자·운영자 화면과 정상 지급.
3. P2에서 실제 SP, 동시성, 두 재화, 예약 배치 및 재실행 완성.
4. P3에서 장애 보상 기능을 도입하는 **실제 스키마/SP 변경** 실험.
5. P4에서 실제 SQL 병목을 만들어 측정하고 튜닝.
6. P5에서 같은 지급 시나리오를 HA 환경에서 다시 검증.
7. P6에서 데이터 삭제 사고를 격리된 복원 인스턴스로 PITR.
8. P7에서 축적한 수작업 절차를 CLI/테스트 하네스로 자동화.
9. P8(선택)에서 CloudNativePG 전환과 마이그레이션을 연구.

## 7. 시나리오 평가 양식

모든 실험은 다음 순서의 증거를 요구한다.

- 사건 발생 전: 초기 스키마, row 수, 트래픽, DB 설정, DBMS 버전.
- 재현: 명령/SQL, 시작 시각, 예상 장애, 안전한 실험 환경.
- 조사: 앱 오류와 DB 통계·로그를 함께 수집.
- 원인: 확인된 현상과 추정만 있는 현상을 구별.
- 선택지: 2개 이상 대응의 비용·장단점 비교 가능한 경우 비교.
- 변경: SQL/설정/아키텍처 diff와 배포 절차.
- 검증: 같은 워크로드 기준 전·후, 3회 이상 반복, 회귀 테스트.
- 잔여 위험: 이 환경에서 실험하지 못한 장애 조건.

## 8. 핵심 설계 위험

- **범위 확장:** 비즈니스 기능 과다 개발 방지; 주인공은 DB 운영.
- **가짜 성능 문제:** 데이터가 크다는 이유만으로 Slow Query를 가정하지 않음.
- **과장된 HA:** 같은 호스트 Docker는 호스트 장애 대응이 아님.
- **어색한 Backfill:** `ADD COLUMN ... DEFAULT 'EVENT'`는 기존 모든 행의 물리 UPDATE 없이 작동할 수 있음. 대량 Backfill 시나리오는 별도 실제 변환을 정의.
- **트랜잭션 경계:** SP 내부에 강제 COMMIT/ROLLBACK 작성하지 않음. Spring Boot와 워커가 호출 트랜잭션을 소유.
- **증거 누락:** 데이터 손실·복구 시간을 관측 전부터 0, X초라고 문서화하지 않음.
