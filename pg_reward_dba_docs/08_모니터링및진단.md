# 08. 모니터링 및 진단 설계

## 1. 지표를 네 계층으로 구분

| 계층 | 지표·이벤트 | 진실의 원천 |
|---|---|---|
| 클라이언트/부하 | 요청 전송 수, HTTP 상태, Timeout/UNKNOWN, 요청 p95 | 부하 실행기 외부 로그 |
| API/워커 | PAID/REPLAYED/ALREADY_GRANTED/ERROR, DB 호출·COMMIT 결과, 배치 실행 정보 | 구조화 애플리케이션 로그 |
| 업무 데이터 | `reward_grants`, `wallet_ledger`, `wallets`, `event_recipients` | 복구 후 실제 PostgreSQL 행 |
| DBMS | 활성 세션, Lock, SQL 실행 통계, WAL·복제 위치, 백업/아카이브 | PostgreSQL 내부 뷰·로그 |

**Q1 결론:** API의 성공·실패 건수는 API/클라이언트 로그에서 확인하고, 실제 지급 완료는 DB 커밋 후 `reward_grants`로 확인. DB 도달 전 오류는 지급 테이블에 남지 않음. 클라이언트의 Timeout은 성공·실패 중 하나로 함부로 분류하지 않는다.

## 2. 필수 수집 필드

- `experiment_id`, `scenario_id`, 타임존 포함 timestamp
- `event_id`, `user_id`(테스트 ID), `request_id`, `batch_run_id`
- `request_start`, `response_end`, HTTP 결과, 오류 종류
- DB commit 성공 확인 여부, `grant_id` (있을 때)
- PostgreSQL `server_version`, DB 설정 snapshot, DB host/role 정보
- 데이터 건수/분포, 사용한 SQL 쿼리 버전, Git SHA

## 3. SQL 실행 통계

```sql
-- 사전: pg_stat_statements 확장과 shared_preload_libraries 적용 필요
SELECT queryid, calls, total_exec_time, mean_exec_time,
       rows, shared_blks_hit, shared_blks_read, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

- `pg_stat_statements`에 SQL 실행 시간의 **p95 필드가 기본 제공되지는 않는다**.
- p95를 원하면 부하 실행기에서 개별 SQL 실행 시간을 수집하거나 별도 히스토그램을 구축.
- API p95는 DB 외 다른 구간도 포함하므로 DB 원인을 직접 증명하지 않음.

## 4. Lock/세션

```sql
SELECT pid, state, xact_start,
       wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocking_pids, query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

- Lock 요청 종류와 각 Lock의 획득 여부는 `pg_locks`로 추가 확인.
- `ALTER TABLE ADD COLUMN` 등 대부분의 `ALTER TABLE` 형태는 `ACCESS EXCLUSIVE` Lock이 필요할 수 있음.
- 사용자가 보는 **응답 지연**과 DBA가 확인하는 **잠금 대기**를 연결할 때 동일 시각 로그가 중요.
- P5에서는 `idle in transaction` 상태의 세션과 `Lock/transactionid` Waiter를 `pg_blocking_pids()`로 연결하고, 조치 뒤 데이터와 대기 상태를 재검증.

## 5. 복제 상태(P7)

Primary:

```sql
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_backlog_bytes
FROM pg_stat_replication;
```

Standby:

```sql
SELECT pg_is_in_recovery() AS standby_mode,
       pg_last_wal_receive_lsn() AS receive_lsn,
       pg_last_wal_replay_lsn() AS replay_lsn;
```

- LSN 차이는 **바이트 위치 차이**이다. 이를 바로 ‘지연 10ms’라고 표시하지 않는다.
- 시간 기반 지연은 별도 정의된 시각·커밋/재생 이벤트로 계산하고, 유휴 상태에서 `pg_last_xact_replay_timestamp()`만 보고 오판하지 않도록 한다.
- 복제 접속이 끊기면 지표가 NULL/행 부재일 수 있으므로 상태와 함께 해석.

## 6. WAL/체크포인트/백업

- P2 Crash Recovery: PostgreSQL 재시작 로그, 체크포인트 및 REDO 관련 시각·메시지 보존.
- P4 대량 변경: 작업 전/후 WAL LSN 차이, WAL 증가량, 스토리지 사용량 기록.
- P6 Archive: `pg_stat_archiver`, 아카이브 파일 연속성, 백업 복원 성공 기록.
- PostgreSQL 버전마다 통계 뷰 컬럼명이 달라질 수 있으므로 선택한 버전(17)에서 실행 점검 필수.

## 7. 화면에 표시할 정보

**사용자 UI:** 지급 버튼/결과, 지갑 Money·Point, 원장 타임라인, 재시도/미확정 안내.

**운영자 UI:** 이벤트 상태, 대상 총수/커밋 지급수/미지급 수, 배치 최근 실행/오류, CS 지급 검색(P3).

**DBA UI(Grafana/CLI 우선):** DB 접속, 실행 중 SQL, Blocker→Waiter, Replication Lag(단위 명시), WAL, 최근 배포, 백업 복원 결과.

초기에는 UI 지표를 DBMS 관측 기능의 대체물로 간주하지 않는다. 같은 데이터의 근거 SQL과 수집 시각을 추적할 수 있어야 한다.
