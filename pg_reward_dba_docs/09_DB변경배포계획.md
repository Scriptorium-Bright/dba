# 09. DB 스키마·SP 변경 및 배포 계획

## 1. 변경 요구의 출발점

이벤트 보상만 있던 초기 원장에 고객지원 장애 보상이라는 두 번째 지급 출처가 도입된다. 기존 테이블은 `reward_grant_id NOT NULL`이어서 장애 보상 기록을 표현할 수 없다.

## 2. 변경 전·후 모델

**v1:** `wallet_ledger(user_id, reward_grant_id NOT NULL, currency_type, amount)`.

**v2:** `source_type(EVENT/COMPENSATION)`, `reward_grant_id NULL`, `compensation_id NULL`을 두고 두 FK 중 출처에 맞는 하나만 존재하도록 CHECK/FK로 보호. `compensations`에는 요청 ID, 사유, 운영자, 금액 스냅샷을 보존.

실행 migration은 V7 확장 → V8 nullable/FK/CHECK `NOT VALID` → V9 별도 검증 → V10 CS 지급 procedure → V11 로컬 reset의 보상 출처 반영 순서다. `(event_id, incident_reference, user_id)` UNIQUE는 서로 다른 request ID로 같은 장애 지급이 중복되는 것도 방지한다.

## 3. 배포 방식 — 확장 → 데이터 검증 → 신규 코드 → 제약 강화

| 순서 | 수행 작업 | 호환성/운영 영향 | 검증 |
|---|---|---|---|
| 1 | 현재 스키마·SQL 의존성·호출량·장기 Tx 수집 | 사전 분석 | 베이스라인 보고서 |
| 2 | `compensations` 생성, 신규 컬럼 `source_type`, `compensation_id` 추가 | 기존 코드가 새 필드를 몰라도 실행되도록 구성 | INSERT/SELECT 정상 |
| 3 | `reward_grant_id DROP NOT NULL`, FK·CHECK 추가 계획 | 기존 데이터와 새 데이터 참조 구조 전환 | 원장 무결성 검사 |
| 4 | SP의 이벤트 지급 경로 호환성 검증 후 CS 지급용 SP 추가 | SQL 버전 관리 | 기존 지급·신규 지급 테스트 |
| 5 | CS 운영 화면/API 기능 배포 | 신규 응답 필드·검색 쿼리 | 두 출처의 검색 결과 |
| 6 | Backfill 필요 시 별도 단계로 진행 | 장기 UPDATE/Lock/WAL 영향 | 잔여 NULL·대조 쿼리 |
| 7 | 유효성 검사·제약 강화·운영 결과 기록 | 검증 통과 후 완료 | 회귀 테스트 |

**중요:** `ADD COLUMN source_type TEXT NOT NULL DEFAULT 'EVENT'`의 상수 기본값은 PostgreSQL 11 이상에서 기존 모든 행의 물리적 UPDATE가 없어도 동작할 수 있다. 따라서 *무조건 대량 UPDATE*를 포함하지 않는다. 반면 기존 행마다 다른 값을 산출해야 하는 데이터 이관은 실제 Backfill이 필요하다.

## 4. ALTER TABLE Lock과 장기 트랜잭션

- 일반적인 `ALTER TABLE ... ADD COLUMN`은 `ACCESS EXCLUSIVE` Lock을 필요로 하며, SELECT 등의 잠금과 충돌할 수 있다.
- 컬럼 추가 구문 실행 자체가 빨라도 **기존 Tx 때문에 Lock 획득이 지연**될 수 있다.
- 대기 중인 DDL 때문에 이후 접근도 대기하는 Lock Queue 문제가 생길 수 있다.
- 변경 유형에 따라 테이블 Rewrite, Validation Scan 등이 필요할 수 있으므로 `ALTER TABLE` 종류별로 확인한다.

예시:

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE wallet_ledger ADD COLUMN source_type TEXT NOT NULL DEFAULT 'EVENT';
COMMIT;
```

이 SQL은 v1→v2 실제 변경의 한 단계다. 이미 실행했다면 동일 컬럼을 중복 추가하지 않는다. 실패 시 DDL의 성공/실패와 트랜잭션 상태를 먼저 확인한다.

## 5. 인덱스 변경

```sql
CREATE INDEX CONCURRENTLY idx_wallet_ledger_user_time
ON wallet_ledger(user_id, created_at DESC, id DESC);
```

- **명시적 BEGIN/COMMIT 블록 안에서 실행 금지**.
- Flyway에서는 해당 마이그레이션이 트랜잭션으로 묶이지 않도록 DB별 설정/스크립트 실행 옵션을 확인해야 한다.
- 실패 시 `pg_index.indisvalid` 등으로 INVALID 인덱스 여부를 확인한다.
- 예고 없이 인덱스를 추가한다고 성능이 반드시 개선되지는 않는다. 조회/쓰기·디스크 비용 함께 비교.

## 6. Backfill이 필요한 변경의 처리

예: 과거 원장 행을 외부 이벤트/보상 원인 식별자에 매핑하는 새 컬럼이 도입되어, 기존 행마다 다른 값으로 채워야 하는 상황.

- 대상 수·디스크·WAL 여유·복제 지연 기준 측정.
- 작은 범위(예: PK 5000건) 단위로 갱신 후 각 Tx 커밋하는 방식 검증.
- 재시작 가능 조건: `WHERE new_column IS NULL` 및 처리된 행 수/검증 오류 기록.
- 동시 온라인 쓰기와 경합·분리 수준 확인; SKIP LOCKED를 사용할지 데이터 정확성 요구에 맞게 결정.
- Backfill 중 전체 트랜잭션 하나가 길어지지 않게 설계.
- 인덱스·Constraint 검증은 단계적으로 적용, 잠금 영향 계측.

## 7. 배포 실패 시 대응

**배포 전:** 백업/복원 가능 여부, 현재 DDL, 새 앱과 구 앱의 호환성, 잠금 타임아웃 준비.

**변경 도중 실패:** 적용 완료된 Migration 버전 확인, 일부 성공한 비트랜잭션 DDL(예: CONCURRENTLY) 상태 점검, 중복 재실행 전에 실제 객체 상태 확인.

**새 기능 배포 후 실패:** 기능 플래그/앱 롤백 가능 여부, 이전 SP/데이터 형식과의 호환성, 데이터가 이미 v2 형식으로 쓰였는지 평가. 모든 변경을 단순 DROP으로 되돌리지 않는다.

**결과 보고:** 변경별 실행 시각, Lock 대기·오류, 변경 소요 시간, 지급 서비스 영향, 무결성 대조, 되돌림/Forward Fix 선택 근거.

## 8. P3의 구체적 실험

- 실험 A: 사용자 요청이 계속 들어오는 상황에서 ADD COLUMN(메타데이터 중심).
- 실험 B: 장기 Tx가 DDL Lock 획득을 지연시키는 경우.
- 실험 C: 실제 기존 데이터 계산이 필요한 Backfill을 별도 데이터셋에 추가.
- 실험 D: SP 교체 중 이전 API 요청과 새 API 요청의 호환성.
- 실험 E: 잘못된 legacy `source_type` 행 때문에 constraint validation이 실패하는 상황과 원인 행 forward fix 후 재시도.

**완료 기준:** 단순 ‘마이그레이션 성공’이 아니라 문제 원인·변경전후·서비스 영향·실패 대응을 함께 제출한다.
