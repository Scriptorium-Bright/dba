# 02. 요구사항 분석서

**상태:** v2.0 요구사항과 P0~P5 실행 기록을 기준으로 관리한다. 요구사항 ID는 실험 스크립트, 결과 파일, 실행 문서에서 동일하게 사용한다.

## 1. 기능 요구사항 — BF

| ID | 행위자 / 기능 | 입력 | 구체적인 처리 | 출력·예외 | 완료 기준 | Phase |
|---|---|---|---|---|---|---|
| BF-01 | 사용자 / 이벤트 목록·상세 | 상태 필터, 이벤트 ID | 이벤트 상태·기간·방식·Money·Point·내 수령 여부 조회 | 목록, 상세, 존재하지 않음 | 화면과 DB 상태 일치 | P1 |
| BF-02 | 운영자 / 이벤트 생성 | 이름·기간·지급액·지급 방식·예약 시각 | DRAFT 저장 및 유효성 검증 | event_id, 검증 오류 | CLAIM/BATCH 분기 정상 | P1 |
| BF-03 | 운영자 / 이벤트 OPEN·CLOSED | event_id, 전이 명령 | 유효한 상태 전이 및 상태 변경 이력 기록 | 적용 상태 | 비정상 전이 거부 | P1 |
| BF-04 | 사용자 / 직접 수령 | event_id, request_id | 이벤트 검증 → `reward_grants` → 지갑 → 원장 한 트랜잭션 | PAID/REPLAYED/ALREADY_GRANTED/NOT_AVAILABLE/ERROR | 중복 지급 0, 지급 1회 | P1~P2 |
| BF-05 | 사용자 / 지갑·원장 조회 | 사용자 ID, 커서·한도 | Money·Point 잔액, 이벤트 지급 내역 조회 | 지갑, 최신순 원장 | 지급 후 실제 상태 노출 | P1 |
| BF-06 | 운영자 / 배치 대상 설정 | event_id, 사용자 명단 | 대상자 테이블 등록, 중복 및 존재 검증 | 등록된 대상 수 | 확정 대상 명단 조회 가능 | P2 |
| BF-07 | 배치 작업자 / 예약 일괄 지급 | event_id, 실행시각·배치 크기 | 지급 대상 조회 → 사용자별 SP 호출 → 커밋 → 결과 기록; 미완료 재조회 | 완료/보류/미확정 수 | 재실행에도 1인당 1회 지급 | P2 |
| BF-08 | 운영자 / 이벤트 보상 변경 | event_id, 변경 Money·Point | 향후 신규 지급에 적용, 변경 감사 기록 | 전·후 값 | 기존 지급 스냅샷 유지 | P2 |
| BF-09 | CS / 장애 보상 지급 | user_id, Money·Point, 사유, 요청 ID | `compensations` + 지갑 + 원장 원자적 지급 | 보상 지급 ID | 이벤트/보상 모두 이력에 표시 | P3 |
| BF-10 | CS / 지급 내역 검색 | 사용자·기간·출처·커서 | 이벤트 지급/장애 보상 원장 통합 조회 | 조건 검색 결과 | 과거·신규 데이터 정합 | P3 |
| BF-11 | 운영자 / 작업 상태 확인 | 배치 이벤트 ID | 대상 총수, 실제 커밋 지급수, 미지급 수 및 최근 실행 오류 조회 | 집계와 상태 | DB 테이블과 일치 | P2 |

`BF-02`는 `CLAIM`/`BATCH` 오타가 없도록 구현 시 ENUM 값 고정: `CLAIM`, `BATCH`.

## 3. 비기능 요구사항 — NFR

| ID | 항목 | 요구 기준 및 측정 방법 |
|---|---|---|
| NFR-01 | 원자성 | 지급 기록·지갑 잔액·원장 반영이 동일 트랜잭션에 포함. 오류 시 세 변경 모두 취소 |
| NFR-02 | 멱등성 | 같은 이벤트·사용자·요청 재시도에 추가 재화 증가 0; 다른 요청 ID도 중복 지급 0 |
| NFR-03 | 복구 후 일치 | 실제 지급 1건당 재화 원장 0~2건 및 잔액 대조 일치(초기 잔액/모든 변동 포함) |
| NFR-04 | 가용성 | P7에서 장애→최초 정상 쓰기까지 관측 RTO 기록. 사전 목표치는 기준 측정 후 결정 |
| NFR-05 | 데이터 보존 | 장애 전 확인된 성공 응답과 복구 DB의 지급 기록을 대조, 손실량/RPO 기록 |
| NFR-06 | 성능 | 같은 데이터 분포와 부하로 before/after 비교. 실행계획·I/O·쓰기 영향 포함 |
| NFR-07 | 관측 가능성 | API, 워커, DB 지표를 동일 실험 ID와 시각으로 연결 |
| NFR-08 | 재현성 | 장애·튜닝 실험 각 3회 이상 실시, 조건과 편차 기록 |
| NFR-09 | 변경 안정성 | DDL 잠금·대량 Backfill·SP 교체의 호환성 및 실패 대응 문서화 |
| NFR-10 | 보안/격리 | 위험 실험은 로컬 전용; 실제 비밀번호/개인정보 Git 금지; 분리된 운영 역할 |

| GET | `/api/me/wallet` | BF-05 |
| GET | `/api/me/ledger?cursor=...&limit=20` | BF-05 |

**응답 의미:** `PAID`는 신규 지급 트랜잭션 커밋 후 반환, `REPLAYED`는 이전 요청 결과 재확인, `ALREADY_GRANTED`는 다른 요청으로 이미 지급, `NOT_AVAILABLE`은 대상/기간/상태 불충족이다. `UNKNOWN`은 클라이언트가 최종 결과를 확인 중인 상태이며 SQL 오류와 타임아웃은 별도 오류로 기록한다.

## 5. 예외 및 모서리 사례

- 이벤트 종료 직전 요청과 상태 전환 경합 → 지급 시점의 정책을 일관되게 적용.
- COMMIT 성공 후 HTTP 응답 유실 → 같은 request_id로 조회/재시도; 중복 지급 없음.
- 워커가 100명 단위 처리하다 7번째 트랜잭션에서 장애 → 이전 커밋 유지, 해당 트랜잭션 전체 미확정, 복구 DB로 재조회.
- 지급 원장 INSERT 도중 오류 → 잔액·지급 이력 포함 전체 롤백.
- 지갑 없는 대상자 → 실패가 명확히 기록되며 조용히 지급 성공 처리하지 않음.
- 비동기 Standby Failover → 원 Primary에만 커밋된 지급이 승격 Standby에서 유실될 수 있으므로 **복제 정책과 외부 성공 응답 증거**가 필요.
- PostgreSQL CHECKPOINT는 WAL REDO 시작 지점을 관리한다. 배치 대상과 미지급자는 `event_recipients` 및 `reward_grants` 대조 쿼리로 확인한다.
- API p95는 클라이언트 요청 시간 표본에서 계산하고, SQL 실행 통계와 실행 계획은 DB 구간 분석에 사용한다. `pg_stat_statements`의 호출·누적·평균 실행 시간은 SQL 식별자별로 비교한다.

## 6. 인수 기준과 추적

- 모든 BF/DB/NFR ID에 하나 이상의 TC(테스트 케이스) 연결: [10_검증및실험계획.md](10_검증및실험계획.md).
- P0~P2 인수 조건: 사용자 UI 실제 지급, 관리자 UI 실제 이벤트 운영, 두 재화 정합성, 100개 동시 중복 요청, 재시도·롤백, **예약 일괄 지급 1000명 및 중단/재실행** 테스트.
- **진행 현황:** P3 장애 보상·운영 마이그레이션과 P5 Lock Wait 진단을 기록했다. P6 PITR과 P7 HA/Failover는 다음 운영 실습 단계다.
