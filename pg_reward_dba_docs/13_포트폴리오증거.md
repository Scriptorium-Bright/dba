# 13. DBA/Database Engineer 포트폴리오 증거 설계

> 현재 공고에 맞춘 소개문, 직무요건 매핑, phase별 사례와 면접 정리는 [포트폴리오 문서](portfolio/README.md)에서 확인한다. 이 문서는 프로젝트 전체의 증거 구성과 향후 운영 실습 로드맵을 설명한다.

## 1. 무엇을 보여줄 것인가

채용 분야별 강조점은 다르지만 프로젝트 코드는 하나로 유지한다.

| 평가 역량 | 증거 |
|---|---|
| SQL·RDBMS 기본 | ERD, 제약조건, JOIN/집계 쿼리, 실행 계획 설명 |
| DB 개발 | Stored Procedure, 파라미터, `RETURNING`, 트랜잭션과 동시성 테스트 |
| DB 객체 변경 | 버전별 DDL·SP, Flyway 적용 이력, 배포 검증/차단자 분석 |
| 튜닝 | 문제 SQL, 데이터 분포, EXPLAIN/BUFFERS, 전후 비용과 Trade-off |
| 운영 진단·장애 대응 | 사건 타임라인, 가설, PostgreSQL 세션·wait event, 조치와 복구 뒤 대사 |
| 백업·복구 | WAL/체크포인트 개념, 실제 PITR 복원 로그와 정합성 결과 |
| HA | Primary/Standby 구성, Failover, RTO/RPO·split-brain 위험 분석 |
| 자동화 | Python/Bash CLI, 로그·검증 결과의 반복 재현 |
| 커뮤니케이션 | 요구사항/시나리오 분리, ADR, 런북, 실패 사례와 결정 근거 |

## 3. 사례 소개 형식

**문제 → 분석 → 행동 → 결과 → 비용·한계** 순서를 유지한다.

```md
### [S03] 운영 중 DDL Lock 대기 문제
- 현상: 어떤 요청이 얼마나 지연되는지 (측정)
- 확인: Blocker 세션, SQL, Lock 유형
- 대안: 작업 시각 변경 / 짧은 DDL / 단계 배포
- 선택: 실제 변경 SQL·lock_timeout
- 재검증: 동일 트래픽 조건의 전·후 데이터
- 한계: 단일 노드·로컬 환경, 규모 제한
```

### [P5] 오래 열린 트랜잭션의 행 Lock 진단
- 증상: `p5_waiter_b` UPDATE가 `Lock/transactionid`에서 대기
- 원인: `p5_blocker_a`가 `SELECT ... FOR UPDATE` 후 `idle in transaction`으로 남아 같은 행 Lock을 보유
- 영향 확인: 대기 중인 UPDATE와 별도 SELECT를 나눠 관찰. SELECT는 committed 값 100을 44.823ms에 반환
- 조치와 검증: A를 COMMIT하자 B가 완료되고 값은 101. 실습 harness가 기준값 100으로 복구
- 증거: `pg_stat_activity`, `pg_blocking_pids()`, SQL excerpt, 단조 시계 기반 대기 시간, cleanup 후 잔존 Lock 0건
- 후속 개선 후보: 실제 앱 SQL의 `application_name`을 운영 요청과 연결하고, 업무 트랜잭션 경계에 맞춘 idle-in-transaction 경보 기준을 정함

## 4. 피해야 할 표현

- "RTO 0초", "무손실", "100% HA" 등 조건 없는 성능·신뢰성 주장.
- 실제로 재현하지 못한 Slow Query를 해결했다고 단정.
- 애플리케이션의 중복 방지 동작만으로 DBA 장애 대응 역량을 설명했다고 주장.
- 같은 PC의 Docker Primary/Standby를 실제 다중 호스트 가용성으로 설명.
- AI 도구가 작성한 SQL을 검증 없이 구현 성과로 기재.

## 5. 지원 직무별 서술 방향

**펄어비스 DBA:** 테이블·프로시저 정의, 버전 관리, 검수·패치, 쿼리 튜닝과 Lock의 원리 및 실험을 프로젝트의 실행 기록과 연결해 설명.

**커넥트웨이브 DBA(추가 목표):** PostgreSQL 설치·운영, 백업/복원, SQL 계획·지표, Docker·Linux, Bash/Python 자동화, 이후 CloudNativePG.

**DB Platform/Database Engineer:** 운영 스크립트·CLI·모니터링·반복 실험 도구 자체의 개발 구조 및 설계 선택.

## 6. 최소 증거 세트

- P2: 보상 지급 1회와 100개 동시 요청 결과, 지급/원장/잔액 대조, 중단 후 복구·재실행 결과.
- P3: Migration 전/후 DB 변경 SQL, Lock 차단 관계와 대응 결과.
- P4: 1백만 ledger의 전역/기간 query 계획, 부분 인덱스 개선, WAL·공간 비용과 `CREATE INDEX CONCURRENTLY` 관측.
- P5: Lock Wait incident report, blocker/waiter 관측, 조치 전후 결과와 정합성 대사.
- P6: PITR 복원 지점과 복구 전후 데이터 대사.
- P7: Primary/Standby Failover, 쓰기 역할과 연결 전환, 관측 RPO/RTO.

완료하지 않은 Phase는 로드맵으로 분리하고 완료 사례와 섞지 않는다.
