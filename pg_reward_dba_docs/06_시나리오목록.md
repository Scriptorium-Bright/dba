# 06. 운영·장애 시나리오 카탈로그

## 1. 관리 원칙

- **기본 설계**([01~05])와 **문제 재현 시나리오**를 독립적으로 관리한다.
- 각 시나리오에는 `사건 → 사용자/DB 영향 → 관측 → 가설 → 조치 후보 → 결정 → 전후 검증 → 설계 반영`이 있어야 한다.
- 시나리오마다 계획·실행 상태를 구분한다. 실행 전 수치와 예시는 가정이며, 실측값은 phase 실행 기록과 연결한다.
- 실제 실험 때 시나리오별 하위 폴더에 `README, reproduce.sql, observation.md, decision.md, verification.md, raw/`를 만든다.

## 3. S00 — 정상 직접 수령

- **초기 상태:** 이벤트 A `CLAIM`, 사용자101 잔액 `MONEY=0`, `POINT=0`.
- **조작:** 사용자101이 A를 수령(1,000 MONEY + 200 POINT).
- **DB 기대:** `reward_grants` 1행, 원장 2행, 잔액 `1000/200`.
- **재시도:** 같은 request_id로 다시 요청해도 잔액 불변.
- **검증:** 실제 INSERT ID가 원장 FK와 일치, 전체 COMMIT 확인.
- **개선으로 이어질 수 있는 문제:** 지급 SP 롤백 누락, UNIQUE 부재, DB 호출 여러 트랜잭션 분리.

## 4. S01 — 일괄 지급 중 DB 비정상 종료

**상황:** 이벤트 B 대상 1,000명에게 오전 09:00에 MONEY 500/POINT 100 지급. 가정상 600명의 지급 트랜잭션이 커밋된 다음 PostgreSQL 비정상 종료.

**재현:** P2에서는 격리된 로컬 DB 컨테이너를 비정상 종료시킨다. `docker compose stop` 같은 정상 종료와 구분하여 실제 비정상 종료를 의도적으로 주입한다(정확한 명령은 환경 구축 후 검증).

**관측 순서:**

1. 클라이언트/워커 로그에서 `PAID`, `UNKNOWN`, 실패를 구분.
2. 서버 프로세스/재시작 로그 및 PostgreSQL Crash Recovery 기록 확인.
3. 복구된 `reward_grants`로 실제 커밋 지급자 확인.
4. `event_recipients LEFT JOIN reward_grants`로 미지급 대상 목록 확인.
5. **같은 업무 요청 키로 재실행**하고 최종 총 지급 1,000명, 중복 0건, 원장·지갑 합계 일치 검증.

**DBMS 복구:** 체크포인트가 지시하는 REDO 시작 WAL 위치부터 필요한 레코드를 재생하여 일관된 DB 상태를 만든다. CHECKPOINT는 미지급 사용자를 찾아주지 않는다.

**업무 복구:** 복구된 대상자/지급 기록 차이를 쿼리로 계산하고 미지급만 다시 처리한다.

**개선 후보:** 배치 재실행 절차와 request_id 안정화, 처리 결과 대조 자동화, 사용자별 커밋 vs B건 커밋 비교. `B=100`은 가정일 뿐 최적값이 아님.

**인수 조건:** 복구 후 지급 대상 모두 정상 반영, 추가 중복 지급 0, 최종 일치 검사 통과. **스케줄러 메모리 카운터만으로 지급 완료를 판정하지 않는다.**

## 5. S02 — 고객지원 장애 보상 요구

**상황:** 이벤트 B 장애 이후 CS가 영향 사용자에게 별도 Money/Point 보상을 지급해야 함.

**기존 제약:** `wallet_ledger.reward_grant_id NOT NULL`이라 이벤트 지급 근거만 표현.

**변경 후보:** `compensations` 추가, `wallet_ledger.source_type`과 `compensation_id` 추가, `reward_grant_id` nullable 변경, 출처별 정확한 FK 제약, SP 추가, 화면 통합 조회.

**중요한 점:** `source_type='EVENT' DEFAULT`는 기존 이벤트 원장 전체의 물리 UPDATE가 불필요할 수 있다. 별도로 기존 데이터의 속성을 매핑해야 한다면 Backfill을 설계한다.

**검증:** 변경 중 기존 지급·조회 정상, 신규 CS 지급 정상, 이벤트 원장 유지, 출처별 무결성 검사, 롤백/Forward Fix 절차 검증.

## 6. S03 — DDL Lock 대기와 조회 정체

**상황:** 세션 A가 `BEGIN; SELECT ... FROM wallet_ledger;` 후 종료하지 않음. 세션 B가 `ALTER TABLE wallet_ledger ADD COLUMN ...` 실행. 세션 C가 SELECT 수행.

**재현/관측:** 세션 B는 `ACCESS EXCLUSIVE` 잠금 요청에서 대기 가능. 세션 C의 뒤이은 SELECT도 대기할 수 있음. `pg_stat_activity`, `pg_locks`, `pg_blocking_pids()`로 대기 사슬 확인.

**개선 후보:** `lock_timeout`을 둔 짧은 DDL, 장시간 트랜잭션 정리, 호환성 있는 단계별 변경, 대용량 Backfill의 트랜잭션 단위 조절.

**검증:** 변경 SQL 자체의 실행 시간과 **잠금 획득 대기 시간**을 구분해 기록. 같은 조건에서 요청 오류·대기·트랜잭션 지속시간 비교.

## 7. S04 — 지급 이력 조회 성능 저하

**상황:** 지급 원장이 누적된 뒤 CS의 사용자별 최신 지급 내역 검색이 지연됨.

**진단:** `EXPLAIN (ANALYZE, BUFFERS)`와 `pg_stat_statements`, 테이블 통계, Lock Wait, I/O를 확인. 기준 환경에서 실제로 병목이 나타나는지를 먼저 검증.

```sql
SELECT id, currency_type, amount, created_at
FROM wallet_ledger
WHERE user_id = 101
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**인덱스 후보:** `(user_id, created_at DESC, id DESC)`.

**검증:** 데이터 건수/분포 고정, 전후 실행 계획·실행 시간·읽기 Buffer·인덱스 크기·INSERT 비용 비교. API p95는 사용자 영향 확인용 보조 지표.

## 8. S05 — 서비스 운영 중 인덱스 추가

**상황:** S04 개선 인덱스를 추가할 때 일반 `CREATE INDEX`가 쓰기 요청을 대기시키는지 확인.

**비교:**

```sql
CREATE INDEX idx_ledger_user_time
ON wallet_ledger(user_id, created_at DESC, id DESC);

-- 별도 동일 조건의 DB에서 비교 (같은 이름으로 동시에 만들지 않음)
CREATE INDEX CONCURRENTLY idx_ledger_user_time
ON wallet_ledger(user_id, created_at DESC, id DESC);
```

`CONCURRENTLY`는 일반 INSERT/UPDATE/DELETE를 차단하지 않도록 인덱스를 만들지만 더 오래 걸릴 수 있고 **트랜잭션 블록 내부에서 실행할 수 없다**. 실패 시 INVALID 인덱스 잔재 확인.

## 9. S06 — Standby 잔액 조회 지연

**가설:** Primary에서 지급 COMMIT → API 성공 → 조회는 Standby로 라우팅 → WAL Replay 지연 시 오래된 지갑 값 노출.

**재현:** 격리된 Standby에서 `pg_wal_replay_pause()`로 적용 지연을 만들어 지급 후 오래된 잔액이 보이는지 확인한 후 `pg_wal_replay_resume()`.

**관측:** Primary/Standby의 실제 행 비교, `pg_stat_replication`의 send/write/flush/replay LSN 및 Standby 수신·재생 위치, 요청의 DB 라우팅.

**조치 후보:** 지급 직후 읽기 Primary 강제, Standby 재생 LSN 대기, 동기 복제 `remote_apply` 검토. 커밋 지연·Primary 부하·사용자 일관성 비교.

## 10. S07 — Failover와 RPO

**상황:** Primary 다운, Standby 승격 후 API/Worker 재연결.

**관측:** 장애 시각, 감지, 승격, 최초 정상 쓰기 성공 시각, 외부 성공 응답 내역과 새 Primary DB 대조.

**주의:** 비동기 복제에서 이전 Primary에 성공한 커밋이 Standby에 없을 수 있음. 예전 Primary 재등장 시 fencing/격리 필수. 두 노드 단순 승격만으로 완성된 HA 주장 금지.

**조치 후보:** 동기/비동기 트레이드오프, 타임아웃·Proxy·HA Manager 조정. 실측 RTO/RPO와 쓰기 가능성 비교.

## 11. S08 — 운영자의 데이터 삭제 사고/PITR

**상황:** 원장의 일부 행이 실수로 삭제됨. 해당 DELETE도 Standby에 복제될 수 있음.

**조치:** Base Backup과 연속 WAL Archive가 확보된 상태에서 삭제 직전으로 별도 복구 DB 생성 → 누락 행 및 지갑 정합성 대조 → 필요한 데이터 복원 계획 수립.

**검증:** 복원 시점·WAL 연속성·실제 데이터·복원 소요 시간. 원 DB 자동 덮어쓰기 금지. 삭제 이후 정상 처리된 데이터 보존 계획 필수.

## 12. S09 — 배치 트랜잭션 크기 실험

**가설:** 사용자별 커밋(1명/Tx)과 B명/Tx 사이에서 커밋 빈도·Lock 유지·WAL·실패 시 롤백 범위가 달라짐.

- 후보 `B ∈ {1, 10, 25, 50, 100, 200, 500}` 등.
- 평가 `지급 처리량, Tx 수행시간, p95, Lock Wait, WAL bytes, 실패 배치 재작업 건수, 장애 후 재처리 완료 시간`.
- 한 Tx에서 오류 발생 시 최대 해당 B명의 변경이 롤백될 수 있음. 이미 커밋된 다른 Tx 유지.
- **Parametric Search:** 검증된 단조 제약(예: B 증가에 따라 *측정된 최악 Tx 지속시간*이 단조)일 때만 해당 임계값 탐색에 적용. 처리량/지연/경합은 일반적으로 단조 보장 없음 → 후보별 반복 측정 및 변동성 분석이 기본.
- **Delta Debugging**은 특정 데이터 한 건이 안정적으로 실패를 일으키는 경우 별도의 원인 축소 방식. 랜덤 DB 장애의 원인 진단과 혼동하지 않음.

## 13. S10 — 열린 트랜잭션의 행 Lock 대기

**상황:** 세션 A가 `SELECT ... FOR UPDATE`로 테스트 행을 잠근 뒤 트랜잭션을 끝내지 않는다. 세션 B의 UPDATE가 같은 행에서 대기한다.

**진단:** `pg_stat_activity`의 상태·wait event·SQL과 `pg_blocking_pids()`를 연결해 B의 Blocker가 A인지 확인한다. `pg_locks`에서 관련 relation/transactionid Lock을 함께 본다.

**영향 확인:** 세션 C의 SELECT를 대기 중 실행해 committed 값과 완료 시각을 확인한다. UPDATE 대기와 일반 읽기의 상태를 나눠 기록한다.

**조치와 검증:** A의 트랜잭션과 SQL을 확인한 뒤 COMMIT/ROLLBACK 중 하나를 선택한다. B가 완료됐는지, 결과 행이 한 번 반영됐는지, fixture가 기준값으로 돌아왔는지 대사한다.

실행 결과와 재현 도구는 [P5 운영 진단 기록](implementation/exec/p5.md)에서 확인한다.

## 14. S11/S12 — 확장 후보

- **S11 MVCC/VACUUM:** 장시간 트랜잭션으로 죽은 행 버전 정리가 지연되는 조건 재현 → `pg_stat_user_tables`, 장시간 트랜잭션, 테이블 크기 분석.
- **S12 WAL/디스크:** 부하·대량 Backfill로 WAL/스토리지 사용이 증가 → 사용량 알람, 아카이빙 적체, 작업 중단/복구 절차 실험.
