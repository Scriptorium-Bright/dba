# 12. 설계 결정 기록

프로젝트에 반영한 주요 데이터 모델·트랜잭션·배포·진단 결정을 근거와 함께 기록합니다.

## 1. 확정된 결정

| ID | 결정 | 근거와 영향 |
|---|---|---|
| ADR-001 | 지갑은 `money_balance`와 `point_balance`를 보유 | 두 게임 재화를 독립 원장 행으로 기록하고 재화별 합계를 대사합니다. |
| ADR-002 | 이벤트 지급은 `CLAIM`과 `BATCH`로 구분 | 사용자 직접 수령과 예약 대상 일괄 지급을 같은 지급 원장으로 관리합니다. |
| ADR-003 | `reward_grants`를 공통 지급 사실로 사용 | 이벤트·사용자 유일성, 요청 키, 지급 시점 금액 snapshot을 한 테이블에서 보장합니다. |
| ADR-004 | BATCH 지급은 사용자별 트랜잭션으로 커밋 | 커밋 단위가 분명해지고 재실행 시 미지급 사용자만 선택할 수 있습니다. |
| ADR-005 | 복구 후 업무 대상은 대상 명단과 커밋된 지급 행으로 계산 | PostgreSQL Crash Recovery와 애플리케이션의 미지급 재처리 단계를 분리합니다. |
| ADR-006 | 도메인은 기간 이벤트 보상으로 한정 | API 흐름을 유지하면서 지급 기록·원장·Lock·실행 계획 실습에 집중합니다. |
| ADR-007 | 운영 경로는 UI, DB 진단 경로는 SQL·CLI로 구성 | React는 사용자 영향을 보여주고, PostgreSQL 도구는 세션·Lock·계획·복구 상태를 관측합니다. |
| ADR-008 | 기반 지급 흐름을 완성한 뒤 장애·성능 시나리오를 추가 | P2 정합성 결과를 P3 schema 변경, P4 조회 튜닝, P5 Lock 진단의 기준으로 사용합니다. |
| ADR-009 | 고정 기본값 컬럼 추가와 행별 Backfill을 구분 | PostgreSQL 17의 컬럼 추가 동작과 실제 P3 migration을 기준으로 DDL 작업량을 결정합니다. |
| ADR-010 | API 지표와 DB 지표를 출처별로 기록 | API 요청 시간은 사용자 관측값으로, `pg_stat_statements`와 `EXPLAIN`은 SQL 실행 정보로 사용합니다. |
| ADR-011 | `wallet_ledger.user_id`를 사용자별 조회용으로 중복 저장 | 복합 FK가 지급 행의 사용자와 ledger user의 일치를 보장하고 `(user_id,id DESC)` 경로를 지원합니다. |
| ADR-012 | `wallet_ledger.source_type`을 출처 구분자로 저장 | source FK의 NULL 패턴에서 결정되는 값을 CHECK로 고정해 API 조건과 P4 부분 인덱스 predicate에 공통 사용합니다. |
| ADR-013 | 지갑 잔액은 현재 값 요약, 지급 원장은 변동 근거로 유지 | 한 트랜잭션에서 두 테이블을 함께 갱신하고 reconciliation SQL로 잔액과 원장 합계를 대조합니다. |
| ADR-014 | 보상 업무 키와 요청 내용 일치를 별도로 검증 | 같은 업무 키와 같은 payload는 `ALREADY_COMPENSATED`, payload 충돌은 HTTP 409로 응답합니다. V13 acceptance에서 순차·동시 요청을 확인했습니다. |
| ADR-015 | P4 인덱스는 조회 선택도와 추가 WAL·크기를 함께 비교 | 8컬럼, 50,000행의 공통 scratch fixture에서 네 구성을 측정하고 partial key-only와 all-source 인덱스를 용도별로 적용했습니다. |
| ADR-016 | V15 concurrent index를 P4 전용 Flyway location으로 관리 | 비트랜잭션 migration과 exact catalog 검증을 분리해 fresh 적용, 실패 이력 복구, populated table 적용 흐름을 재현합니다. |

## 2. 데이터와 트랜잭션 용어

- PostgreSQL 프로시저는 `CREATE PROCEDURE`로 정의하고 `CALL`로 실행합니다. PL/pgSQL 함수도 데이터 변경문을 실행할 수 있습니다.
- `RETURNING id INTO v_grant_id`는 INSERT가 생성한 지급 ID를 절차 변수에 저장합니다. 외부 성공 응답은 호출 트랜잭션의 COMMIT 뒤에 반환합니다.
- WAL과 체크포인트는 PostgreSQL Crash Recovery의 복구 기준을 구성합니다. 업무 미지급 대상은 `event_recipients`와 `reward_grants`를 조회해 계산합니다.
- `CREATE INDEX CONCURRENTLY`는 일반 DML이 진행되는 동안 인덱스를 만들며 명시적 트랜잭션 블록 바깥에서 실행합니다.
- `source_type`은 EVENT/COMPENSATION을 구분합니다. V8 CHECK는 source FK 중 정확히 하나만 설정하도록 하고, 출처별 복합 FK가 지급 소유자를 확인합니다.

## 3. 이어서 설계할 항목

| 주제 | 설계 방향 |
|---|---|
| PITR | base backup과 WAL archive를 별도 복원 인스턴스에 적용하고 지급·원장 정합성을 대조합니다. |
| HA/Failover | Primary/Standby, 장애 감지, fencing, 연결 전환, 재동기화 절차를 측정합니다. |
| 다중 BATCH worker | worker 점유, 잠금 범위, 재시도와 업무 키 경합을 정의합니다. |
| 정정·차감 원장 | 음수 변동, 원거래 연결, 잔액 재구성 규칙을 별도 모델로 설계합니다. |
| 운영 목표 | 반복 측정과 업무 기준으로 RTO/RPO·지연·알림 임계값을 정합니다. |
